# 长任务、任务状态与可观测性讲述卡

> **一句话目标**：让一个长耗时 Agent 任务“能创建、能查询、能停止、能恢复、能解释为什么失败”。

---

## 一、2 分钟口述答案

> 以成果评审 Agent 为例，我不会让 HTTP 请求一直等待 GitLab 快照、仓库事实提取和 LLM 裁决完成。创建接口先校验输入和幂等键，快速返回任务 ID；后台执行器再推进 `queued`、校验、采集、评估、组装草稿等状态，并持续持久化阶段、进度、心跳和处理计数。前端可以通过查询接口轮询任务状态；如果用户取消，系统先记录 `cancel_requested`，执行器在 GitLab 批次、LLM 批次或图节点的安全检查点协作式停止，最终进入 `canceled`。外部请求和阶段都有 timeout/deadline，失败会记录错误码和审计。服务重启后，遗留活动任务在启动阶段标记为 `interrupted`，不在读取接口自动续跑，之后可以创建关联的新任务重试。这样任务不是黑盒：用户和开发者都能知道它在哪里、为什么停止、是否可以重试。

## 二、状态机速画

```text
POST 创建 + idempotency_key
        ↓
queued → validating → collecting → evaluating → assembling → pending_review → human_confirmed
  │             │            │             │
  └─────────────┴────────────┴──────────→ cancel_requested → canceled
                  任意执行异常/超时 → failed
                  服务重启遗留活动状态 → interrupted

failed / canceled / interrupted → 新建 queued（retry_of_task_id）
```

### 每个设计点回答什么问题

| 设计 | 回答的问题 |
| --- | --- |
| `task_id` | “这次异步工作是谁？” |
| `idempotency_key` | “重复请求会不会启动两次？” |
| 状态/阶段/进度 | “任务现在做到哪里？” |
| 心跳/处理计数 | “是在慢还是卡住？” |
| error code | “失败属于哪类问题，能否重试？” |
| 审计 | “谁在何时触发了什么动作？” |
| retry link | “这次重试对应哪次失败？” |

## 三、轮询、WebSocket 与消息队列

| 技术 | 适合 | 不适合替代 |
| --- | --- | --- |
| 轮询 | 状态变化频率不高、实现简单、允许秒级延迟 | 不等于后端任务调度或可靠投递 |
| WebSocket | 需要实时多事件推送、连接治理能力充足 | 不等于任务持久化、取消或重试机制 |
| 消息队列 | 削峰、异步解耦、可靠投递/消费协调 | 不自动解决业务幂等、状态机或最终一致性 |

**项目边界**：当前可确认的是任务状态查询、进度、取消、重试与审计；轮询/WebSocket/消息队列以设计取舍方式回答，不说成已有系统实现。

## 四、日志、Trace ID、Task ID 的关系

- **Task ID**：面向长任务业务生命周期，查询状态、结果、重试关系。
- **Trace ID**：面向一次跨服务请求链路，关联网关、API、数据库、外部调用日志。
- **日志**：记录事件、参数摘要、耗时、错误码和异常上下文。

> 当前项目已有任务状态、审计、阶段/进度、错误码和日志事实；是否已接入完整 Trace/指标告警平台需核实。面试不能把“日志存在”说成“全链路可观测性已完整建设”。

## 五、长任务接口白板设计

```text
POST /tasks
  输入：业务参数 + idempotency_key
  输出：task_id、status、进度链接

GET /tasks/{id}
  输出：status、stage、progress、heartbeat、error_code、result_summary

POST /tasks/{id}/cancel
  前置：仅活动状态；写 cancel_requested

POST /tasks/{id}/retry
  前置：failed/canceled/interrupted；新建任务并关联原任务

GET /tasks/{id}/audit
  输出：状态变化、阶段、错误摘要、关键时间
```

## 六、常见错误表达

- 不说“异步接口就是后台任务”，应说明执行器、状态持久化、取消与恢复如何设计。
- 不说“取消任务就是杀线程”，应说明协作式检查点的可控性与延迟。
- 不说“有日志就可观测”，应区分任务 ID、Trace、指标、告警和回放。
- 不说“消息队列保证不重复”，应说明幂等仍由业务端处理。

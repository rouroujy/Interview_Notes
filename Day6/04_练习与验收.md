## 一、白板题：设计一个可重试的 Agent 任务接口

### 5 分钟作答顺序

1. 画 `POST /tasks`：输入参数、`idempotency_key`、快速返回 `task_id`。
2. 画任务状态机：正常主线、`cancel_requested → canceled`、`failed`、`interrupted`、重试新建任务。
3. 画 `GET /tasks/{id}`：状态、阶段、进度、心跳、错误码、结果摘要。
4. 写外部调用控制：超时、有界并发、阶段 deadline、安全检查点。
5. 写持久化：任务、审计、重试关系；避免长事务包住外部调用。
6. 写边界：轮询/WebSocket 只是通知方式，幂等和状态机不能省。

### 参考答案

> 我先用幂等键解决重复创建，再用持久化状态让长任务脱离单个 HTTP 请求。外部调用前后在安全检查点检查取消和 timeout，任务完成或失败都写稳定状态和审计。重试不覆盖旧任务，而是创建带关联的新任务。服务重启时把遗留活动任务标中断，避免读取接口触发隐式续跑。这样用户可以查询、取消和判断能否重试，工程上也便于排障。

## 二、Edge 同步速画

```text
内网 GitLab
   ↓（Edge 本地读取）
游标定位增量 → 写 SQLite Outbox → 批次发送中心
                                      ↓
                        幂等键去重 + 持久化 + 审计
                                      ↓
                      成功确认 / 失败保留 Outbox 重试
```

**必须说出的四句**：

1. “Edge 主动同步避免中心主动暴露跨网访问。”
2. “Outbox 解决待发送数据在网络失败下的留存和重试。”
3. “游标解决增量范围定位，重叠/重试可能重复，所以中心还要幂等。”
4. “这是至少一次投递加幂等处理，不承诺恰好一次。”

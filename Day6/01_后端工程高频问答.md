# Day 6：后端工程高频问答

> 共 36 题。每题都要补一句项目映射或事实边界；不要把通用方案说成已经上线的架构。

---

## 1. FastAPI 的优势是什么？

**答案**：FastAPI 基于类型注解和 Pydantic 做请求校验与文档生成，适合快速构建 Python 服务接口；也支持依赖注入、异步路由和异常处理。我的项目使用 FastAPI 承接质量分析、代码评审等服务接口，但框架本身不自动解决长任务、权限和事务问题。

## 2. FastAPI 的依赖注入适合做什么？

**答案**：适合注入数据库会话、鉴权信息、配置、共享服务等横切依赖，减少路由手动创建资源。依赖的生命周期和异常释放要明确，不能把长生命周期连接或跨请求状态随意放在全局变量中。

## 3. Pydantic 解决什么问题？

**答案**：它把输入输出变为 schema，校验类型、必填、范围和格式，减少接口边界的脏数据。它不能保证业务正确，例如合法 ID 不代表有权限、合法时间范围不代表查询成本可接受。

## 4. FastAPI 的 `async` 接口一定更快吗？

**答案**：不一定。`async` 更适合 I/O 等待可让出事件循环的任务，如异步 HTTP、数据库驱动或文件 I/O；CPU 密集计算、阻塞 SDK、长时间同步解析放在事件循环会阻塞其他请求。项目中的长任务需要后台执行、并发限制或独立 worker 思路，而不是只把函数改成 `async`。

## 5. 什么不适合直接放在事件循环？

**答案**：CPU 密集模型推理、巨大 PDF 解析、阻塞网络库调用、长时间同步循环和大量本地文件处理。应考虑线程池、进程、任务队列或外部 worker，并控制资源和取消边界；具体选型取决于任务性质和部署条件。

## 6. 协程、线程、进程如何选择？

**答案**：协程适合高并发 I/O；线程适合包装阻塞 I/O 或短后台工作，但受 GIL 和共享状态影响；进程适合 CPU 密集且需要并行计算的任务。代码评审当前以后台线程承载任务生命周期，同时对远端 GitLab/LLM 调用做有界并发和超时；不应因此推断已实现分布式 worker。

## 7. GIL 的基本影响是什么？

**答案**：CPython 的 GIL 使同一进程内多个线程不能同时执行 Python 字节码，因此线程对 CPU 密集计算的并行收益有限；但 I/O 等待时线程仍可提升并发。它不等于“Python 不能并发”。

## 8. 如何设计统一异常处理？

**答案**：区分参数/业务/权限/外部依赖/系统异常，映射为稳定错误码与安全消息；日志保留必要上下文，响应不泄露 Token、SQL、完整敏感数据或内部堆栈。评审任务会把超时、取消、重启中断等映射到不同状态和错误码。

## 9. 什么是后台任务接口的合理边界？

**答案**：短、可控、与请求生命周期弱耦合的任务可用应用内后台机制；长耗时、需重试、进度、取消、持久化恢复或多实例协调的任务需要明确任务模型和更可靠的执行架构。代码评审已将状态、进度、取消和重试持久化，不能仅靠一次 HTTP 请求等待完成。

## 10. 如何设计幂等任务创建接口？

**答案**：客户端为同一业务意图带稳定 `idempotency_key`，服务端在唯一约束或原子写入下查找/创建任务；重复请求返回同一任务而不重复启动执行。代码评审任务已支持幂等键，解决双击、超时重试和网络重放。

## 11. 重试为什么创建新任务而不直接复用旧任务？

**答案**：旧任务保留原失败状态、错误码、输入快照和审计，便于排障；新任务可从干净生命周期开始，并通过 `retry_of_task_id` 关联旧任务。直接把旧任务改回运行中会模糊历史和并发状态。

## 12. 长耗时 Agent 的接口如何设计？

**答案**：创建接口快速返回 `task_id` 与初始状态；查询接口返回状态、进度、阶段、心跳、错误码和结果摘要；提供取消、重试、确认等受限动作；结果和审计独立持久化。评审 Agent 已体现这条链路。

## 13. 为什么取消要采用协作式取消？

**答案**：强杀线程可能让数据库事务、文件写入和远端连接处于不确定状态。协作式取消先写 `cancel_requested`，任务在远端调用/批次/节点安全检查点发现后收尾为 `canceled`，更可控但不是瞬时取消。

## 14. 服务重启时活动任务怎么处理？

**答案**：启动时识别上次进程遗留的活动任务，标为 `interrupted`，记录稳定错误码和审计；由人工或受控重试创建新任务。评审服务采用启动阶段协调，而不是在查询接口中隐式恢复。

## 15. MySQL 索引的作用是什么？

**答案**：索引加速筛选、排序、连接等访问路径，代价是写入维护成本和存储。索引设计要从真实查询条件、选择性和排序/连接模式出发，而不是给每列都加索引。

## 16. 什么情况下索引可能失效或效果差？

**答案**：在索引列上做函数/隐式类型转换、前导通配符模糊匹配、联合索引不满足最左前缀、选择性很低、范围条件后再利用后续列受限等场景，优化器可能不走预期索引。实际判断要用执行计划和慢查询，而不是死背规则。

## 17. 联合索引最左匹配如何理解？

**答案**：联合索引按列顺序组织，查询从最左列开始连续匹配时通常更容易利用索引。索引顺序应结合高频过滤、连接和排序条件设计；范围条件后的列能否继续有效取决于具体查询和优化器。

## 18. 什么是事务 ACID？

**答案**：原子性确保一组操作要么全成功要么回滚；一致性保证约束前后满足；隔离性控制并发互相影响；持久性保证提交后可恢复。任务创建、状态变更和审计记录需要考虑这些边界。

## 19. 常见隔离级别与风险？

**答案**：读未提交可能脏读；读已提交避免脏读但可能不可重复读；可重复读提供更稳定快照但需理解幻读/锁行为；串行化最强但并发最低。项目中不应虚构具体数据库隔离配置，面试可说明选择取决于一致性与吞吐要求。

## 20. 如何处理数据库事务与外部调用？

**答案**：避免长时间持有数据库事务再等待远端 API/LLM。通常先持久化任务意图并提交，再执行外部调用；结果回写时用新的短事务和状态校验。这样降低锁占用，也便于失败重试和恢复。

## 21. 什么是 N+1 查询？

**答案**：先查 N 条主记录，再对每条额外查关联数据，导致 1+N 次查询。可用预加载、批量查询、聚合或调整数据访问层解决；是否需要优化要看真实查询量和执行计划。

## 22. SQLAlchemy 的优缺点？

**答案**：优点是模型化、参数化、会话/事务管理和跨数据库抽象；缺点是复杂查询可能不直观、容易产生 N+1 或隐藏 SQL。关键查询仍要理解生成 SQL、索引和执行计划。

## 23. Alembic 的作用是什么？

**答案**：Alembic 管理数据库 schema 的版本化迁移，使表结构变更可审查、可复现、可在不同环境顺序执行。迁移要同时考虑数据回填、兼容窗口、回滚和部署顺序，不等于自动保证数据正确。

## 24. 什么是分页，深分页有什么问题？

**答案**：分页限制一次返回量。`offset` 深分页会扫描/跳过大量行且在数据变动下可能重复或漏数据；大数据量场景可考虑基于稳定排序键的 keyset/cursor 分页。Edge 同步的游标是按同步位置定位增量，不等同于普通页面分页。

## 25. Redis 适合缓存什么？

**答案**：适合读多写少、可重建、计算/访问成本高且允许短暂陈旧的数据，例如论文项目中的可复用解析或检索结果。缓存不是数据库真相来源，key 需包含文档/索引版本，具体 TTL 和实现以项目记录为准。

## 26. 什么是缓存穿透、击穿、雪崩？

**答案**：穿透是反复请求不存在数据绕过缓存；击穿是热点 key 失效瞬间大量请求打到数据库；雪崩是大量 key 同时失效或缓存整体故障。可分别用空值/布隆过滤、互斥/逻辑过期、过期时间打散/限流降级等思路；不要说项目已实现除非有事实。

## 27. 缓存与数据库不一致怎么处理？

**答案**：先明确谁是事实源，通常数据库为准；写入时可用更新数据库后删除缓存等策略，并接受短暂不一致或通过版本/消息机制改善。关键是选择一致性目标和失败补偿，不承诺绝对实时一致。论文项目具体策略未核实。

## 28. 分布式锁有什么风险？

**答案**：可能发生锁过期但任务未完成、客户端暂停、误释放他人锁、时钟/网络问题等。锁应有唯一 token、过期和续约策略，并把幂等作为最终保护；不要用“加锁”替代业务去重和状态机。

## 29. Docker 镜像与容器有什么区别？

**答案**：镜像是只读的构建产物和依赖模板，容器是镜像运行出的实例，带可写层和运行状态。部署时应把代码、依赖、配置入口和数据持久化边界分开。

## 30. Dockerfile 分层为什么重要？

**答案**：分层影响构建缓存、镜像大小和构建速度。稳定依赖层应尽量放在变化频率低的位置，源码放后面；同时避免把密钥写进镜像层。

## 31. 环境变量和数据卷分别解决什么？

**答案**：环境变量注入不同环境的配置和密钥引用，数据卷持久化数据库文件、Outbox、报告或日志等运行数据。Edge SQLite Outbox 若只放容器可写层，容器重建可能丢失，因此需要持久化卷。

## 32. Docker 化 Edge 同步解决什么？

**答案**：把 Edge 服务、依赖和启动方式打包，减少分公司环境差异，便于部署、升级和回滚。它不自动解决网络授权、数据备份、资源限制或配置安全，这些仍需单独设计。

## 33. Outbox、游标、幂等接收如何协作？

**答案**：Outbox 可靠保存待发批次并允许失败重试；游标确定下一次增量同步范围；中心端用批次幂等键去重。同一数据因至少一次投递可能重复，幂等保证重复处理不产生重复写入；三者解决不同故障窗口，缺一不可。

## 34. 为什么不能承诺恰好一次？

**答案**：网络超时无法判断中心是否已收到，Edge 重试就可能重复；要在跨网络端到端实现严格恰好一次需要更复杂的协议、事务边界和外部系统支持。当前工程安全说法是至少一次投递加中心幂等处理。

## 35. 轮询和 WebSocket 如何选择？

**答案**：状态变化频率低、实现简单且允许小延迟时可轮询；需要实时推送、多事件和长连接治理时可考虑 WebSocket。代码评审已有状态/进度查询事实，但是否已使用 WebSocket 未确认，面试要说成取舍而非已有实现。

## 36. 日志、Trace ID、Task ID 分别解决什么？

**答案**：日志记录事件和错误上下文；Trace ID 串联一次跨服务请求链路；Task ID 标识长任务生命周期、状态和结果。当前项目有任务 ID、阶段/进度、审计和日志；完整分布式 Trace 平台需按实际情况说明。

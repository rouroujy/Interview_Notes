# 项目工程化映射：从知识点回到真实设计

> **使用方式**：面对后端八股题，先讲通用原理，再立刻落到一个真实项目点，最后补充事实边界。

---

## 一、质量管理体系 Agent：数据边界与跨网同步

| 后端知识 | 项目真实映射 | 面试关键句 | 边界 |
| --- | --- | --- | --- |
| FastAPI / Pydantic | 企业 Agent 以 FastAPI 提供服务，参数需经过 schema、业务和权限校验 | “模型参数与接口输入都不是可信事实，服务端必须再验证。” | 具体路由与鉴权方案以代码/部署记录为准 |
| MySQL / SQLAlchemy | 结构化 Bug、Commit、需求等数据需要关系型存储和查询 | “统计口径由数据库和指标工具计算，而非放进向量库。” | 不虚构表规模、索引或 SQL 性能数据 |
| ToolRegistry | Agent 通过受控工具查询指标，不直连 DB/API | “把访问路径收敛到工具层，便于校验、审计和测试。” | 不说所有工具都由本人独立实现 |
| Edge 主动同步 | 中心不能主动访问内网 GitLab 时，Edge 本地读取并向中心发送 | “不扩大中心跨网访问面，由内网侧主动同步。” | 网络、证书、生产拓扑细节需核对 |
| SQLite Outbox | 待发送批次本地持久化、失败重试 | “先记住要发什么，再处理网络成功与否。” | 备份、磁盘监控等需以实际部署核实 |
| 游标增量 | 确定新增/更新数据的同步范围 | “游标避免每次全量拉取，重叠窗口防漏，重复交给幂等。” | 具体窗口、批次大小以代码配置为准 |
| 批次幂等 | 中心按稳定批次标识去重 | “至少一次投递时，重复发送不能导致重复写入。” | 不承诺恰好一次 |
| 多实例隔离 | 以实例/组织维度隔离数据和配置 | “隔离不能只靠一列字段，接口、查询、缓存与日志都要携带隔离维度。” | 物理库表隔离不是已确认事实 |
| Docker | Edge 服务环境一致化与交付 | “镜像解决环境一致，数据卷和配置安全仍需单独保证。” | 不虚构容器编排/K8s |

## 二、成果评审 Agent：长任务与可审计交付

| 后端知识 | 项目真实映射 | 面试关键句 | 边界 |
| --- | --- | --- | --- |
| 任务创建 | `idempotency_key` 避免重复创建 | “网络重试和用户双击都返回同一任务，而不重复执行。” | 幂等键生命周期策略需以实现为准 |
| 后台执行 | 后台线程执行任务生命周期 | “HTTP 创建请求不等待评审完成，任务状态独立持久化。” | 不说已使用消息队列/分布式 worker |
| 有界并发 | 并发任务使用限制，GitLab blob 读取也有上限 | “吞吐要受外部系统、内存和配额约束，不能无限并发。” | 压测容量数据未确认 |
| 进度与心跳 | 阶段、进度、处理计数、心跳持久化 | “前端能区分正常执行、卡住、超时和取消。” | 不说已有完整实时推送 |
| 协作式取消 | `cancel_requested` 在安全检查点被消费 | “避免强杀线程破坏事务和资源状态。” | 取消不是毫秒级即时生效 |
| deadline / timeout | GitLab/LLM 请求 timeout，快照/事实/裁决阶段 deadline | “外部调用和阶段都有上限，失败有稳定错误码。” | 具体生产配置无需背数值 |
| 重启恢复 | 启动时遗留活动任务标为 `interrupted` | “不在读接口偷偷续跑，由人工决定重试。” | 不说已实现通用断点续跑 |
| 审计 | 状态事件、阶段、计数、错误码、哈希等记录 | “审计保留可排障信息，同时不落源码正文、Token、完整 prompt。” | 完整 Trace/监控平台未确认 |

## 三、论文引用查证 Agent：缓存与可复现服务

| 后端知识 | 项目真实映射 | 面试关键句 | 边界 |
| --- | --- | --- | --- |
| FastAPI | 将解析、检索和验证封装为服务接口 | “接口负责接收任务、校验输入和返回明确异常状态。” | 具体异步任务接口实现未核实 |
| Redis | 简历确认使用 Redis 缓存 | “缓存适合复用解析或检索这类成本高、可重建的中间结果。” | key、TTL、失效与一致性实现未核实 |
| Docker | 简历确认 Docker 化交付 | “固化 GROBID 和依赖环境，减少本地/服务端差异。” | 不说生产集群规模 |
| 日志 / 异常 | 记录解析、检索、验证失败并降级 | “PDF 解析失败或证据不足要给可定位原因，而非强行输出结论。” | 不虚构完整告警系统 |

## 四、统一工程叙事（可直接口述）

> 我在项目里逐渐形成一个工程习惯：先定义请求和数据边界，再把不确定或长耗时部分建模为可查询任务。结构化输入用 schema、业务和权限校验；外部调用有 timeout、并发与失败策略；结果、状态和必要审计信息持久化；不确定结论通过无法确认或人工确认降级。质量 Agent 重点是跨网数据同步和指标工具边界，评审 Agent 重点是长任务状态与证据审计，论文项目重点是解析/检索缓存和证据不足降级。它们不是同一个系统，但工程原则一致。

## 五、JD 追问：高并发、分布式、多租户如何诚实回答

> 我已有的事实是：评审任务有有界并发、超时、阶段 deadline、取消/重试和重启中断处理；Edge 有多实例数据隔离、Outbox、游标和中心幂等；服务使用 Docker 化交付。对于真正的高并发容量、分布式队列、K8s 弹性、全链路 tracing、复杂多租户权限模型，我会说明需要补充压测、限流、容量规划、观测和故障演练，不能把当前 MVP 的控制措施夸大成完整平台能力。

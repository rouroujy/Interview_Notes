# 项目卡：前端与全栈经历

> **主线**：前端不是“画页面”，而是管理实时数据、用户操作、接口失败和跨端状态的一致性。

---

## 一、轻舟货运飞船前端：1 分钟介绍

> 我参与过轻舟货运飞船的地面站遥测监控与货物辅助管理前端。项目面向航天领域地面站，页面覆盖遥测数据表格和趋势图、摄像机预览、灯光控制、报警监控、货架可视化和操作记录，并通过语音事件触发交互闭环。技术上使用 Vue3、Vue Router、Vuex、Axios、ECharts 和 Ant Design Vue。项目中一个重要问题是实时刷新和用户操作会冲突：如果页面不断回填最新状态，用户正在进行的灯光或设备控制可能被覆盖。因此我设计了用户交互期间暂停刷新、操作结束后恢复并重新拉取状态的机制；同时对遥测、报警、货物和语音事件做周期刷新，通过事件去重、路由跳转和状态管理保证告警或语音指令发生后各页面状态一致。不同部署环境的后端地址通过运行时配置解耦，使同一构建产物可以适配不同服务地址。

## 二、系统功能与前端职责

| 模块 | 用户目标 | 前端关注点 |
| --- | --- | --- |
| 遥测表格/趋势图 | 查看设备状态与变化趋势 | 周期刷新、时间序列展示、异常态提示、图表性能 |

## 三、实时刷新与用户操作冲突

### 问题

> 监控页面需要周期性获取后端状态，但控制类页面存在用户正在填写参数、确认设备操作或查看局部详情的过程。若定时刷新直接覆盖本地状态，会造成表单丢失、开关回跳、操作反馈不一致，用户会误以为控制失败或系统状态混乱。

### 口述解决思路

> 我将“后端最新状态”和“用户正在编辑/提交的本地状态”区分开。当用户进入控制或编辑交互时，暂停相关数据的自动回填或只更新不冲突区域；操作提交后等待接口结果，再恢复刷新并以服务端确认状态为准。对于报警和语音等事件，使用事件标识或业务键去重，避免同一事件多次触发跳转或重复提示。核心不是简单停止定时器，而是明确哪些状态可自动覆盖、哪些状态必须由用户动作或接口确认驱动。

### 白板图

```text
周期刷新 / 事件到达
        ↓
是否存在用户编辑或控制操作？
   ├─ 否 → 拉取并回填最新状态
   └─ 是 → 暂停冲突区域刷新 / 缓存待更新标记
                     ↓
              用户提交操作
                     ↓
        接口成功/失败提示 + 状态确认
                     ↓
          恢复刷新并以服务端状态回填
```

### 风险与替代方案

| 方案 | 优点 | 风险/适用边界 |
| --- | --- | --- |
| 周期轮询 | 简单、兼容性好、易排障 | 有延迟和重复请求，频率需控制 |
| WebSocket | 低延迟推送、多事件实时更新 | 长连接、鉴权、断线重连和资源治理更复杂 |
| 乐观更新 | 交互快 | 控制失败时必须回滚并提示，不能替代服务端确认 |
| 全局暂停刷新 | 简单 | 可能错过其他重要状态，宜按模块/交互粒度控制 |

**事实边界**：简历确认轻舟项目采用周期刷新和暂停/恢复机制；是否使用 WebSocket 未确认，只作为方案对比。

## 四、事件去重、路由与状态管理

### 事件去重

> 周期拉取与事件推送/语音触发可能重复描述同一报警。应以事件 ID、报警 ID 或“业务键 + 时间窗口”判断是否已处理；去重状态放在适当的全局状态或事件层，避免每个组件各自判断导致不一致。具体去重键和窗口以实际实现为准，不虚构参数。

### 全局状态与路由

> Vuex 适合存放跨页面共享的遥测摘要、报警状态、货物状态或当前选中对象；Vue Router 负责从全局告警/语音事件跳转到相应页面并携带必要上下文。局部表单临时状态不应全部放全局，否则刷新与回滚会变复杂。

## 五、运行时配置为什么重要

> 构建时写死后端地址会让同一份前端产物只能对应一个环境。运行时配置将 API 基地址等环境差异放到部署时读取的配置中，使开发、测试、不同现场环境能复用同一构建产物；但要注意配置加载失败的默认行为、环境变量安全和前端不能保存敏感密钥。

## 六、当前企业平台前端：可核验工程补充

> 这是与轻舟项目**不同**的当前代码库事实：企业质量平台前端使用 React 18、TypeScript、Vite、React Query、Axios、Ant Design 和 ECharts。代码评审页对活动状态任务每 3 秒条件轮询，任务结束后停止刷新；页面支持创建、取消、人工确认、报告下载，并对加载失败展示可操作提示。该实现可用于说明我理解“前端如何消费后端任务状态”，但不能说轻舟项目使用 React 或 React Query。

### 与后端任务状态的端到端讲述（60 秒）

> 对长耗时评审任务，前端提交表单后不等待完整结果，而是获得任务 ID 和初始状态。页面查询任务列表，在任务处于 queued、collecting、evaluating 等活动状态时按固定间隔刷新，展示进度、阶段和错误；用户可对合法活动状态发起取消，对待人工确认任务发起确认。后端负责幂等、状态机、审计和恢复，前端负责根据状态启停轮询、限制不合法按钮、展示失败信息与引导重试。这样轮询只是状态展示通道，不把业务可靠性压在前端。

## 七、旧全栈与第三方接口经历

### 可直接讲的事实

- 参与 SaaS“健身助手”的研发维护，主导“剧帮主”从 0 到 1，覆盖 PC、小程序和 PHP/MySQL 后端。
- 实现预约管理、会员管理、公众号推送、支付与第三方电子签名合同对接。

### 第三方回调通用回答

> 第三方支付或电子签名回调不能只看“收到请求就更新订单”。首先校验签名、时间戳和回调来源；其次按平台事件/订单号做幂等，重复回调不能重复扣款、重复发合同或重复通知；然后校验回调金额、状态和业务订单是否匹配；最后记录原始摘要、处理结果和失败原因，并通过主动查询或对账补偿处理不确定状态。具体使用了哪家支付、签名算法、消息队列或对账频率，需要以旧项目记录核对，不能补造。

## 八、常见错误表达

- 不说“我做了实时系统”，应说“实现周期刷新与事件联动；实时推送方案需和 WebSocket 取舍区分”。
- 不说“刷新时直接覆盖页面状态”，应说“区分服务端状态与用户交互中的本地状态”。
- 不把当前 React/React Query 平台说成轻舟 Vue3 项目。
- 不说“支付回调一定只来一次”，应主动说明验签、幂等和对账。

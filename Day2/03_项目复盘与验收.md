## 一、口述练习

### 1 分钟项目介绍

> 我构建了一个面向企业质量管理场景的 Agent，接入禅道 BUG、GitLab Commit、飞书需求文档和质量体系文件，帮助用户查询质量指标并得到有依据的分析结果。我的重点工作是将不同数据按职责拆分：缺陷等级、功能分布等结构化事实通过受控工具和指标引擎计算；质量体系文件通过 RAG 提供规范依据；LLM 负责理解问题、编排工具和基于事实归纳。对于分公司 GitLab，因为中心不能主动访问内网，我实现了 Edge 主动同步、SQLite Outbox、游标增量和批次幂等接收，将数据接入中心质量看板。面试中应强调：数据或依据不足时不能让模型把推测写成确定事实。

### 3 分钟讲述顺序

- [ ] 背景：质量数据分散且人工跨系统分析成本高。
- [ ] 风险：直接让 LLM 分析会产生统计错误和无依据结论。
- [ ] 总体方案：结构化工具、RAG、LangGraph、LLM 归纳和信息边界表达。
- [ ] Edge 分支：中心不能访问内网，Edge 主动同步，Outbox/游标/幂等分别解决什么问题。
- [ ] 个人职责：工作流、工具边界、需求变更标注、同步接入的参与边界。
- [ ] 可靠性：参数校验、证据来源、信息边界表达、审计，以及高风险场景可采用的业务复核思路。
- [ ] 改进：评估集、链路追踪、故障演练和数据质量治理。

### 5 分钟项目深挖检查

- [ ] 能讲出一个“为什么不用更简单方案”的取舍：不把所有数据直接交给 LLM/RAG。
- [ ] 能讲出一个工程难点：跨网络 GitLab 数据主动同步。
- [ ] 能讲出一个可靠性难点：意图或证据不足时的降级。
- [ ] 能讲出一个扩展方式：新增指标或数据源时修改工具/配置层。
- [ ] 能诚实说明当前没有确认的量化指标，并提出评估方案。

## 四、常见风险表达修正

| 不建议这样说 | 更准确的表达 |
| --- | --- |
| “LLM 不会幻觉。” | “对结构化事实和规范结论增加工具、证据和校验，降低无依据判断风险。” |
| “Outbox 保证数据绝不丢失。” | “Outbox 提供本地持久化和可重试基础，实际可靠性还需要结合事务边界、监控和故障演练验证。” |
| “系统是实时同步的。” | “当前能确认的是 Edge 主动增量同步；实时性指标需要以实际部署与监控数据为准。” |
| “幂等就不会有数据问题。” | “幂等主要处理重复提交；漏数、冲突和数据质量问题还需要额外检测和补偿。” |
| “我做了整个 Agent。” | “我重点参与了工作流、工具边界、需求变更标注和数据接入相关设计/实现。” |
| “检索不到就让模型自己总结。” | “检索不到足够依据时，不把推测当作规范结论，并说明缺少的数据或条款。” |

# 质量管理体系 Agent：项目与技术问答

> **使用方式**：每个问题先练 30 秒版本，再练 1–2 分钟完整版本。所有“可能追问”均附答案；没有当前事实依据的结果，统一说明验证方式或下一步计划，不编造线上指标。

## 1. 请介绍一下质量管理体系 Agent

### 参考答案

这个项目面向企业内部质量管理场景，接入禅道 BUG、GitLab Commit、飞书需求文档和质量体系文件，帮助研发和质量团队查询指标、分析质量问题，并得到有依据的回答。

我在项目中构建了“意图识别 → 受控工具调用 → 结果生成”的 LangGraph 主流程，并设计 ToolRegistry，将缺陷等级、功能分布、激活和需求变更等指标封装为可调用工具。结构化事实通过工具和指标引擎计算，质量体系文件和 checklist 通过 RAG 提供条款依据，LLM 负责理解问题和基于已有信息归纳。对于分公司 GitLab，中心系统不能主动访问内网，我实现了 Edge 主动同步，通过 SQLite Outbox、游标增量和中心批次幂等接收将 Commit 数据安全接入中心质量看板。整体目标是降低自然语言分析中的无依据判断风险；信息不足时，面试中应明确说明结论边界，而不是把推测说成事实。

### 可能追问与答案

#### 你在项目中具体负责什么？

简历中可以确认我完成了 LangGraph 主流程构建、ToolRegistry 设计、结构化指标与 RAG 的职责边界设计、LLM 需求变更标注落库，以及 Edge 主动同步架构实现。面试中仍应按你实际编写或主导的模块进一步说明，不能把团队其他成员的实现全部归为个人成果。

#### 项目最终的业务价值是什么？

它把分散在缺陷、代码、需求和规范文档中的信息组织成可查询链路，减少人工跨系统对照；更重要的是，系统不会把模型结论当作无来源事实，而是尽量提供数据和规范依据，对不足信息明确降级，适合质量管理这类对结论可靠性有要求的场景。

## 2. 为什么不把所有数据都直接交给 RAG 或 LLM？

### 参考答案

不同数据类型的最佳处理方式不同。BUG 数量、严重等级分布、功能分布等属于结构化事实，应该通过数据库查询和指标引擎确定性计算；如果交给 LLM 或仅依赖文本检索，容易出现漏算、重复、统计口径不一致或幻觉数字。质量体系文件、流程规范和 checklist 属于文档知识，适合用 RAG 找到原始条款并提供依据。LLM 更适合做意图理解、工具编排和基于已有事实与依据的归纳。

这种分层让模型不承担它不擅长的统计责任，同时保留自然语言交互能力。

### 可能追问与答案

#### 如果把结构化数据转换成文本后放进向量库，是否也可以？

可以作为补充检索手段，但不适合替代正式指标计算。向量检索擅长语义相关性，不保证完整枚举、聚合计算和最新口径一致性。对于“某时间段 P1 BUG 有多少”这类问题，应优先调用确定性工具；向量库可以帮助找到相关说明、历史案例或字段解释。

#### 什么场景可以让 LLM 直接回答？

低风险的摘要、已有事实的改写、帮助用户理解规范条款等场景可以让 LLM 直接生成，但仍要约束输出格式和来源。只要涉及统计结论、合规判断、责任归因或会影响业务决策的结论，就应增加工具和证据；是否引入人工复核取决于具体业务风险，当前简历未将其列为质量 Agent 的既有流程。

## 3. 系统中的 RAG 具体承担什么职责？

### 参考答案

RAG 主要承载质量体系文件、流程规范和 checklist 的检索。用户问“某项做法是否符合规范”或“缺陷处理流程要求是什么”时，系统先根据问题检索相关条款，再把条款内容、来源和必要的元数据提供给 LLM。模型在回答中应基于这些检索结果解释，而不是凭记忆生成规范。

RAG 的定位是“提供依据”，不是替代指标系统，也不是让模型拥有无限知识。检索不到足够相关依据时，应说明依据不足，不能给出肯定的合规性结论。

### 可能追问与答案

#### RAG 检索结果不相关怎么办？

首先要在检索前做好文档解析、切分和元数据过滤，例如按质量体系版本、文档类型、适用范围过滤；其次设置相关性阈值或重排序，避免将低相关片段直接作为依据；最后在生成阶段要求模型只使用通过校验的片段。没有足够相关结果时，应说明“未检索到可支持该结论的质量体系依据”，并提示用户补充范围；高风险场景是否进入业务复核取决于产品规则，不能默认说成已有流程。

#### 为什么不能把整份质量体系文件放进上下文？

整份文档会增加上下文成本和噪声，也不利于模型聚焦具体条款；长上下文并不等于可靠引用。RAG 可以先根据问题定位相关片段，再将有限、可追溯的证据提供给模型，同时保留来源信息。

## 4. LangGraph 工作流如何设计？

### 参考答案

简历可以确认主流程是“意图识别 → 受控工具调用 → 结果生成”。为了在技术面中说明可维护性，我会进一步将它理解为意图识别、参数校验、工具选择、受控工具调用、指标整理、RAG 检索、结果生成和回答边界检查等职责；状态中保存用户问题、标准化参数、已调用工具、结构化结果、检索依据、错误信息和最终回答。除主流程外的细分节点应以实际代码为准。

关键是让每个节点只处理明确职责，并使用结构化状态传递信息。例如意图识别不能直接跳到生成结论，必须先产出可校验的意图和参数；工具失败或数据为空时，状态要携带失败原因进入降级分支；结果生成后还要校验回答是否越过已有事实和证据边界。

### 可能追问与答案

#### 为什么使用 LangGraph，而不是普通 LangChain 链式调用？

普通链式调用适合简单、线性的场景；这个项目需要条件路由、多工具调用、RAG、失败分支和可观察状态，LangGraph 更适合将节点和状态迁移显式化。它能降低流程复杂度，但可靠性仍依赖参数校验、权限控制、工具实现和回答边界控制，不能把框架当作自动可靠性保证。

#### 工作流出现循环调用怎么办？

需要限制最大步骤数、记录已调用工具和参数、检测重复调用模式，并为每个节点定义清晰的终止条件。超过步数或连续无新增信息时，进入澄清或结束分支，并明确说明当前信息不足；是否进入人工复核属于可根据业务风险增加的后续机制，不能直接说成当前已有流程。

## 5. 意图识别错误有什么后果？如何兜底？

### 参考答案

意图识别错误可能导致选择错误指标、错误时间范围、调用不相关工具，甚至把质量规范问题当成统计问题处理。对于质量管理场景，这会造成看似完整但口径错误的回答。

兜底方式包括：使用受限的意图集合和结构化 schema；对模块、时间范围、指标类型等关键参数做校验；低置信度或缺少必填参数时先澄清；工具结果与意图不匹配时不把结果包装成确定结论。对于高风险问题，可根据业务要求增加用户确认口径或人工复核，但应区分这是工程建议还是当前已有实现。

### 可能追问与答案

#### 如何判断意图识别的置信度？

可以结合模型输出的置信信息、结构化字段完整性、规则校验和历史样本评估。更关键的是，不应只依赖模型自己给出的概率；如果关键参数缺失、意图不在允许集合、或同一问题可映射到多个高风险工具，就按低置信度处理并请求澄清。

#### 用户问题本身很模糊怎么办？

例如用户只问“最近质量怎么样”，系统不应该自行猜测时间范围和指标。可以先返回可选维度，如时间范围、模块、缺陷等级和比较基线；也可以给出明确标注为“默认范围”的概览，但不能把默认口径伪装成用户指定口径。

## 6. ToolRegistry 如何设计？

### 参考答案

ToolRegistry 的作用是把可调用能力统一注册和管理。每个工具至少包含名称、用途描述、输入参数 schema、返回 schema、权限要求、数据来源、超时和错误类型。模型只能从注册表中选择允许的工具，不能直接执行任意 SQL 或访问任意接口。

调用时先根据意图选择候选工具，再由系统检查工具存在性、用户权限和参数合法性；通过校验后在固定数据范围内执行，并返回结构化结果和来源信息。这样便于测试、审计、扩展和安全控制。

### 可能追问与答案

#### 新增一个质量指标时需要改哪些地方？

先定义指标口径、数据来源、时间范围和权限，再实现或配置对应查询工具及返回 schema，然后在 Registry 注册工具，并更新意图到工具的映射、参数校验和测试用例。如果指标会影响回答模板或需要规范解释，还要更新生成与证据校验逻辑。这样改动主要局限在指标工具和配置层，而不是重写主工作流。

#### 如何避免 LLM 选择不该调用的工具？

不能只靠 Prompt。应该根据用户角色、当前意图、业务场景和工具白名单做服务端校验；模型给出的只是候选，最终是否执行由 Registry 和权限层决定。对于敏感工具可进一步要求用户确认、限制参数范围或只允许只读查询。

## 7. 工具调用参数如何校验？如何防越权？

### 参考答案

参数校验分为三层。第一层是类型和格式校验，例如时间格式、枚举值、分页大小，可用 Pydantic schema 完成；第二层是业务校验，例如结束时间不能早于开始时间、模块必须属于当前项目、时间范围不能无限扩大；第三层是权限校验，例如用户是否有权限查询特定项目、分公司或敏感字段。

即使模型生成了看似合法的参数，也必须在服务端重新校验。工具只能在预定义的数据源、字段和只读范围内运行，日志要记录调用者、参数、结果摘要和错误原因。

### 可能追问与答案

#### 如何避免 SQL 注入？

不将模型输出直接拼接进 SQL，而是使用参数化查询、预定义指标工具和受限字段映射。动态条件只允许来自 schema 校验后的枚举、时间和标识符；对于排序字段、表名等不能参数化的部分，要使用白名单映射，而不是接受任意字符串。

#### 如果用户有权限看项目，但没有权限看某些敏感字段怎么办？

权限控制不能只做到项目级，还要支持字段级或结果脱敏。工具根据调用者身份决定可返回字段，对无权限字段返回脱敏值或不返回；模型也只能接触经过权限过滤后的结果，避免在生成阶段泄露原始敏感数据。

## 8. 为什么不能让 LLM 直接生成 SQL？

### 参考答案

LLM 直接生成 SQL 的风险包括：统计口径不一致、字段或表使用错误、全表扫描、越权访问、注入风险和难以审计。质量指标通常有稳定业务口径，例如“激活缺陷”“严重等级分布”的定义不应每次由模型临时理解。

因此我更倾向于把常用指标封装成受控工具或固定查询模板，让模型只选择工具并提供结构化参数。这样虽然牺牲了一部分自由度，但在企业质量场景中换来了可测试、可审计和可维护的结果。

### 可能追问与答案

#### 如果用户提出没有预置的新分析需求怎么办？

先判断需求是新增指标、已有指标组合，还是探索性问题。对于高频且口径明确的需求，应新增受控工具；对于探索性分析，可以进入受限的分析流程，但仍要限制可访问数据、查询成本和输出范围。不能为了“灵活”而把生产数据库的自由 SQL 执行权交给模型。

## 9. Edge 为什么要主动同步，而不是中心系统主动拉取？

### 参考答案

中心系统不能主动访问分公司内网中的 GitLab，通常是出于网络隔离和安全边界考虑。因此由分公司内网侧的 Edge 服务主动访问本地 GitLab，再向中心发起受控的出站同步，是更符合网络边界的设计。

这种方式将内网访问能力留在分公司侧，中心只接收经过认证和格式校验的数据；同时 Edge 可以处理本地网络波动、增量读取和待同步缓存。

### 可能追问与答案

#### Edge 服务如何证明自己是可信来源？

需要为每个 Edge 实例分配独立身份，例如实例 ID、凭证或证书，并在中心侧验证来源和签名/认证信息；同步数据还要携带来源实例、批次和版本信息。具体认证方式要根据企业基础设施确定，不能在没有事实依据时声称已经采用某一种协议。

#### 为什么不要求分公司 GitLab 直接暴露给中心？

直接暴露会扩大内网攻击面，也增加网络配置和权限管理复杂度。Edge 主动同步更符合“最小暴露面”原则：内网 GitLab 不直接对中心开放，数据以受控、可记录的方式向外发送。

## 10. SQLite Outbox、游标增量和批次幂等分别解决什么问题？

### 参考答案

SQLite Outbox 负责在 Edge 本地持久化待发送数据，解决中心暂时不可用、服务重启后任务丢失和读取/发送耦合问题；游标增量用于定位已经扫描到的位置，避免每次全量拉取历史 Commit；批次幂等用于处理网络重试造成的重复发送，确保中心重复收到同一批数据时不重复写入。

当前代码中，SQLite 保存批次和按项目保存的 `last_synced_before` 游标；首次无游标时默认回溯 30 天，增量查询保留 5 分钟重叠窗口，单批最多 100 条。同步轮次优先处理历史 `pending` 批次；成功后标记 `delivered` 并推进游标，失败则保留 `pending`、增加 `retry_count` 并记录 `last_error`。中心端先按 `(instance_id, idempotency_key)` 做批次接收幂等，再通过 `(instance_id, project_id, commit_sha)` 的唯一约束做 Commit 级防重。

三者组合后形成“可持久化、可增量、可重试”的同步基础，但不能直接等同于零丢失或高可用承诺。当前核对到的同步服务中不能把代码注释里的“指数退避”直接说成已经实现。

### 可能追问与答案

#### 同步中断时怎么处理？

中断时 Edge 保留 Outbox 中未确认发送的数据和当前处理状态。当前实现的 `tick()` 会优先重试历史 `pending` 批次；恢复后中心根据 `(instance_id, idempotency_key)` 判断批次是否已处理，Commit 层再用复合唯一约束防重。游标在成功投递后推进；失败时批次保留为 `pending`，并记录重试次数和错误。需要区分“已入 Outbox 未发送”“已发送未确认”等状态，避免盲目跳过数据。

#### 重复发送时怎么处理？

中心先以 `(instance_id, idempotency_key)` 查找接收回执；重复批次直接返回已处理结果，不重复写入。正常写入 Commit 时，再以 `(instance_id, project_id, commit_sha)` 做数据层唯一约束防重。当前代码可以确认这两层防重，但不能把它扩展为“所有冲突都会自动进入人工排查流程”。

## 11. 多实例数据隔离如何理解？

### 参考答案

多实例数据隔离是指不同分公司或不同 Edge 实例的数据在同步、存储和查询中都带有清晰的来源边界。例如每条数据和每个批次都关联实例 ID 或组织标识，中心接收时根据该标识进行认证、分区和权限控制，查询质量数据时也不能跨越用户允许访问的组织范围。

它既避免数据串库，也为后续排查“数据从哪里来、由哪个 Edge 同步”提供基础。

### 可能追问与答案

#### 数据隔离只靠数据库字段够吗？

数据库中的组织或实例字段是基础，但不应只依赖它。还需要在鉴权、接口参数、查询条件、缓存键、日志和监控中都携带隔离维度，避免某一层遗漏导致跨实例访问。对于高敏感场景，还可以结合物理库表隔离或更严格的租户策略，具体取决于业务规模和安全要求。

## 12. Docker 化交付解决什么问题？

### 参考答案

Docker 化将 Edge 同步服务及其依赖、运行配置和启动方式打包，减少不同分公司环境差异，便于部署、升级和回滚。它也有利于明确服务依赖、日志路径和数据卷挂载。

但 Docker 不是安全或可靠性的全部答案。敏感配置仍需要安全管理，SQLite 数据需要持久化卷和备份策略，容器重启策略、网络权限和资源限制也要单独设计。

### 可能追问与答案

#### 容器重启会不会导致 Outbox 数据丢失？

如果 SQLite 文件只存在容器可写层，容器重建时有丢失风险。因此 Outbox 数据需要挂载到持久化数据卷，并在部署时明确备份、权限和磁盘空间监控。是否已具备具体备份指标需要以实际部署事实为准，不能凭空承诺。

## 13. 需求变更标注为什么使用 LLM？

### 参考答案

缺陷历史记录和需求说明中包含大量自然语言，需求变更的表达方式多样，单纯依赖关键词和规则很难覆盖上下文、同义表达和隐含关系。LLM 可以在明确标注定义和上下文范围内辅助输出“是否与需求变更相关”的结构化标签及判断依据。

但 LLM 标注不是绝对事实。当前代码已确认将结果写入缺陷记录：`is_req_change_caused` 用 `NULL/1/0` 表示“未判断/是/否”，`req_change_evidence` 保存 LLM 判断依据，供内部追溯和后续分析复用。模型版本、提示词版本、人工抽查和评估集属于需要结合实际经历进一步核对或完善的内容，不能直接说成已实现流程。

### 可能追问与答案

#### 如何降低 LLM 标注错误？

首先明确标注标准、正反例和结构化输出字段；其次让模型输出依据片段，而不是只返回一个标签；然后对高风险或低置信样本进入人工复核，并把错误样本收集为评估集。后续可以比较不同提示词、模型版本或规则辅助方案的表现，但没有评估数据前不应夸大准确率。

#### 为什么要落库，而不是每次实时判断？

实时判断会增加成本和延迟，也可能因模型版本或提示词变化导致同一记录得到不一致结果。落库可以保存原始依据、标注版本和审核结果，便于复用、纠错和审计；需要更新时可以按版本重新标注，而不是覆盖历史结论。

## 14. 如何衡量 Agent 的回答是否可靠？

### 参考答案

可靠性不能只看回答是否流畅。至少要从四层衡量：第一，意图和参数是否正确；第二，工具返回的结构化事实是否与数据口径一致；第三，RAG 是否检索到了足以支持结论的规范依据；第四，最终回答是否只使用了已提供的事实和引用。

可以构建典型质量问题的离线样本，分别评估意图路由、工具选择、参数正确性、指标结果、证据覆盖和最终回答正确性；线上则记录工具调用成功率、空结果率、降级率、人工修改或确认结果。当前没有完整指标时，我会先说明这套评估框架和需要补齐的数据。

### 可能追问与答案

#### 什么是证据覆盖？

证据覆盖关注回答中的关键结论是否都有对应的数据结果或规范条款支撑，而不是只看回答整体是否通顺。例如回答包含三条质量结论，应检查每条是否能指向工具返回的指标或 RAG 检索到的条款；无法对应的结论应删掉、改成待确认或降级。

#### 业务复核是否说明 Agent 不可靠？

不一定。业务复核是根据业务风险设计的责任边界。对于高风险判断，保留复核可以降低错误成本；随着评估集和可靠性数据积累，可以逐步扩大自动化范围。关键是明确哪些结论可自动输出、哪些需要复核，而不是追求表面上的全自动。当前简历未将该机制列为质量 Agent 的既有流程。

## 15. 数据不完整或 RAG 检索不到依据时怎么回答？

### 参考答案

对于这类问题，回答应明确说明“当前数据不足以支持该结论”以及缺少什么信息，例如时间范围、模块数据、对应质量体系版本或相关条款。可以同时返回已经确认的事实，但要与未确认推断分开。除非代码和产品规则能够确认固定文案，否则不把“无法确认”表述为质量 Agent 已实现的唯一返回状态。

不能因为用户期待答案就补充看似合理的归因。对企业质量场景而言，明确边界比生成无依据结论更有价值。

### 可能追问与答案

#### 这样会不会让用户觉得系统不好用？

如果只回复“信息不足”确实体验不好，所以要给出具体原因和下一步动作，例如建议补充项目、时间范围或相关需求文档；同时展示已查到的指标和条款。这样既不越过证据边界，也帮助用户推进问题解决。

## 16. 某模块缺陷激增，系统如何分析？

### 参考答案

我会先澄清“激增”的比较口径，包括时间范围、模块、缺陷类型和对比基线。然后调用结构化工具统计该模块不同严重等级、状态、来源和时间分布，再结合 Commit 变化、需求变更标注和质量体系 checklist 检索相关依据。

最终回答应分三层：已确认的指标事实、基于事实的可能原因、仍需要补充验证的信息。LLM 只负责组织这些内容；如果数据不足以支持某项归因，就明确说明不能确认，而不是直接判断“代码质量下降”或“需求变更导致”。

### 可能追问与答案

#### 如何区分相关性和因果性？

Commit 增加、需求变更和缺陷增长在同一时间发生，只能说明相关线索，不能直接证明因果。回答中应使用“可能相关”“需要进一步核查”等表达，并建议结合具体变更记录、测试覆盖、发布批次和人工分析验证。只有有明确证据链时，才能更强地表达因果判断。

---

## 17. 如果新增一个数据源或质量指标，系统如何扩展？

### 参考答案

先明确新数据源的业务用途、数据所有权、更新方式、权限边界和质量口径。结构化数据源一般新增连接器或同步链路，再封装为工具并注册到 ToolRegistry；文档型数据源则建立解析、切分、索引和检索配置。之后更新意图到工具或检索策略的映射、参数校验、结果 schema、日志和测试。

因为系统将数据接入、工具能力、RAG 和生成流程分层，新增能力的改动可以尽量局限在对应层，而不是改动所有工作流节点。

### 可能追问与答案

#### 新数据源的数据质量很差怎么办？

先明确质量问题是缺失、重复、时间延迟还是口径不一致；在接入层记录来源和质量状态，在工具层对异常数据做过滤或显式标记，在回答层避免将低质量数据当作确定事实。必要时先只用于辅助线索，不直接参与核心指标或自动结论。

## 18. Agent 的安全风险有哪些？

### 参考答案

主要风险包括：用户通过自然语言诱导调用越权工具；模型生成非法参数或过大查询；RAG 文档中出现提示词注入内容；不同组织或分公司数据串读；日志中泄露敏感信息；以及外部数据同步来源不可信。

对应控制是：服务端工具白名单和权限校验、schema 与业务范围校验、文档来源治理和检索结果隔离、组织/实例维度的数据隔离、日志脱敏和审计、Edge 身份认证与中心端幂等接收。Prompt 约束是辅助，不能替代服务端控制。

### 可能追问与答案

#### 如何处理 RAG 中的 Prompt Injection？

把检索文档视为不可信数据，而不是系统指令。系统提示中明确文档只能作为业务事实或规范依据；对文档内容进行来源管理和必要清洗；模型不能因为检索片段中的指令改变工具权限或输出策略；最终工具调用仍由服务端白名单和鉴权控制。

---

## 19. 这个项目当前有什么局限？下一步如何改进？

### 参考答案

当前最需要持续完善的是评估和可观测性。系统已有结构化指标、检索依据、工具边界和降级思路，但要进一步证明可靠性，需要构建典型质量问题的离线评估集，分别衡量意图识别、工具选择、参数正确性、证据覆盖和最终回答质量。

工程上，我会补充从用户问题、工具调用、检索命中到最终回答的链路追踪；同步链路方面会结合实际部署补充故障演练、数据一致性检查和资源监控；产品上会让用户看到数据来源、时间范围和信息不足原因，减少黑盒感。

### 可能追问与答案

#### 你会优先做哪一项？

我会优先做离线评估集和链路追踪。评估集帮助判断问题到底出在意图、工具、检索还是生成；链路追踪帮助线上定位问题。没有这两项，就很难用数据驱动后续优化，也难以安全扩大自动化范围。

---

## 20. 你从这个项目中最大的收获是什么？

### 参考答案

最大的收获是，我更明确地理解企业 Agent 的难点不在于把模型接上数据源，而在于给不同信息分配正确的责任边界，并对不确定性负责。结构化事实需要确定性计算，规范解释需要证据检索，LLM 适合受约束归纳；跨网络数据要考虑同步、幂等和隔离；高风险结论不能被模型包装成确定事实，必要时可以根据业务风险增加复核机制。

这套思路也影响了我后续的成果评审 Agent 和 AI Coding Harness：我会优先考虑证据、上下文、任务状态和人工责任边界，而不是只追求一次生成结果。

### 可能追问与答案

#### 如果重新设计一次，你会做什么不同？

我会更早把评估集、数据口径和可观测性纳入设计，而不是等到主链路跑通后再补。对于每个关键结论，我会从一开始定义它需要哪些数据或文档证据、缺失时如何降级、怎样记录人工反馈。这样后续迭代会更可量化，也更容易向业务方解释系统边界。

## 面试答题总原则

- 先说明结论，再解释架构或原因。
- 结构化事实、规范依据、模型归纳和可选的业务复核机制必须分开讲。
- 回答同步链路时，明确区分“已设计/已实现的机制”和“尚未用数据验证的指标”。
- 被问到不确定的具体实现时，先说明自己负责的边界，再给出合理的工程处理思路。
- 不用“完全避免幻觉”“保证零丢失”“绝对实时”等绝对表述。

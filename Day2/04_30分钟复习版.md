# Day 2：30 分钟复习版——质量管理体系 Agent

> **目标**：只记一条主线：企业质量数据如何进入系统、如何被可靠分析、LLM 为什么不能越权、跨网段数据怎样安全同步。

## 0–5 分钟：1 分钟项目介绍 + 关键词回忆

### 1 分钟答案

> 我参与开发的质量管理体系 Agent 面向企业内部质量管理场景，接入禅道 Bug、GitLab Commit、飞书需求文档和质量体系文件。核心设计是分清责任边界：缺陷数量、严重等级、模块分布等结构化事实由指标引擎和受控工具计算；质量体系条款和 checklist 通过 RAG 提供依据；LLM 负责意图理解、选择允许的工具和归纳已有事实，不自行编造统计结论。对于中心系统不能主动访问分公司内网 GitLab 的情况，采用 Edge 主动同步，并用 SQLite Outbox、游标增量和批次幂等接收保证可靠性。信息不足、依据缺失或工具失败时，系统明确说明边界并降级，而不是给出看似确定的回答。

### 六个锚点

`业务问题 → 数据分层 → ToolRegistry → RAG 依据 → LLM 归纳 → Edge 可靠同步`

## 5–12 分钟：白板主图

```text
禅道 Bug / GitLab Commit / 飞书需求文档 / 质量体系文件
                ↓
结构化数据：Connector → 标准模型/数据库 → 指标引擎 → ToolRegistry
规范性知识：文档切分/检索 → RAG 来源与条款
                ↓
LangGraph：识别意图 → 受控工具调用 → 规则/依据 → LLM 归纳
                ↓
可追溯回答 / 数据不足或无依据时明确降级 / 人工核查

分公司内网 GitLab：Edge 主动拉取 → SQLite Outbox → 中心幂等接收
```

### 画完必须说出的三句

1. “RAG 不是结构化数据仓库，统计指标必须由确定性计算产生。”
2. “LLM 负责理解和归纳，不负责凭自然语言创造业务事实。”
3. “中心不能拉内网时由 Edge 主动同步，可靠性靠 Outbox、游标和幂等。”

## 12–20 分钟：8 个必答问题

### 1. 为什么不把 Bug 数据直接放进 RAG？

> Bug 是频繁变化的结构化业务事实，数量、时长、比例等需要精确口径和权限控制；向量检索不能替代数据库查询和指标计算。RAG 适合检索制度、条款和 checklist 依据。

### 2. ToolRegistry 解决什么？

> 它把允许 Agent 调用的能力统一注册、参数校验和审计，避免 LLM 直接访问数据库、拼 SQL 或随意调用外部系统；新增能力也能在受控边界内扩展。

### 3. RAG 检索不到制度依据怎么办？

> 返回“未检索到足够依据/需要人工确认”，同时给出可核查方向；不能把模型常识说成公司的制度。

### 4. 为什么中心系统不主动拉分公司 GitLab？

> 因为内网的网络和安全边界不应为了中心访问而被动暴露。Edge 部署在能访问本地 GitLab 的网络中，由它主动向中心同步更符合最小暴露原则。

### 5. SQLite Outbox 的作用？

> 先把待发送事件与本地处理状态可靠落到本地队列；网络失败不会丢数据，可按状态重试，避免“已拉到数据但未成功发到中心”后无从恢复。

### 6. 游标增量与重叠窗口解决什么？

> 游标记录上次同步位置，只拉新增或更新数据；重叠窗口降低边界时间、延迟写入或排序问题导致漏数的风险，重复由幂等接收处理。

### 7. 批次幂等接收如何做？

> 每批使用稳定幂等标识，中心保存已处理标识；同一批重复到达时返回已有处理结果而不重复写入。它解决网络重试或 Edge 重发。

### 8. 需求变更为什么用 LLM 标注又要落库？

> 缺陷描述中的需求变更原因需要语义理解，LLM 适合给出受约束标注；标注要带证据并落库复用，避免每次查询重新判断，也便于人工抽检和修正。

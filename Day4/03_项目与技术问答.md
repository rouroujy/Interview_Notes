# Day 4：论文引用查证 Agent 项目与技术问答

> 使用方式：先口述，再看答案。所有数值、模型名、参数与线上结果以实际记录为准；当前材料只使用简历已确认的项目事实。

---

## 1. 请介绍论文引用查证 Agent。

**答案**：这是一个基于 LLM 的论文引用查证系统。它先用 GROBID 将论文 PDF 解析为 TEI XML，提取结构化文本并切分、向量化；再使用 BM25、FAISS 和 Rerank 组成 Hybrid RAG，为引用主张检索可定位证据；最后基于引用上下文和证据输出结构化判断。评估使用人工标注集，关注 Recall@k、证据覆盖率和判定准确率；工程上通过 FastAPI、Redis、Docker、日志和异常处理交付，证据不足时明确返回无法确认。

**追问：你的个人价值是什么？**  **答**：按简历可说我构建了 PDF 解析、检索、引用验证和工程化服务链路；具体模块的独立完成比例、模型与指标数值应以项目记录核对，不夸大为全部独立完成。

## 2. 为什么不让大模型直接读整篇论文并判断？

**答案**：整篇论文可能超出有效上下文，且 PDF 内容和引用位置难以稳定定位；模型也可能把主题相近、常识或推测当成原文证据。先解析、检索并提供带来源的证据，可以控制上下文、降低成本，并让人复查结论依据。

**追问：长上下文能替代 RAG 吗？**  **答**：不能简单替代。长上下文适合有限且边界明确的材料，但引用查证仍需要定位、过滤和证据覆盖；大文献库或多篇文献场景中，检索和元数据过滤仍有价值。

## 3. 为什么选择 GROBID？TEI XML 有什么价值？

**答案**：学术 PDF 结构复杂，纯文本抽取容易打乱双栏、章节和参考文献。GROBID 面向学术论文解析，TEI XML 保留标题、章节、段落、参考文献等结构，便于按语义边界切分、做元数据过滤和输出来源定位。

**追问：解析失败怎么办？**  **答**：将解析失败或结构不完整作为明确状态返回，不能继续假设文本完整；可提示人工查看原 PDF，表格/OCR 等能力作为后续方案需与实际实现区分。

## 4. chunk 应如何设计？

**答案**：以段落、章节和引用上下文等语义边界优先，并保留论文、章节、段落位置、引用标记等元数据。chunk 过大导致主题混杂、检索不精确、成本升高；过小会丢掉实验条件、限定语和结论上下文。具体长度、重叠和分段策略应通过标注集验证。

**追问：为什么不固定按 500 字切？**  **答**：固定长度可作为实现手段，但不能替代语义边界；尤其论文结论与条件可能跨句或跨段，机械切分容易破坏证据完整性。

## 5. 元数据过滤有什么作用？

**答案**：它把检索范围限制在正确论文、章节或文献标识上，减少同名文献、主题相似但来源错误的候选；同时提供来源展示、调试与审计信息。元数据是检索质量的一部分，不只是展示字段。

**追问：过滤太严格的风险？**  **答**：可能直接把正确证据排除，降低 Recall；所以过滤字段和策略要在标注集上验证，并把无结果与错误过滤区分开。

## 6. BM25 和 FAISS 各自适合什么？

**答案**：BM25 擅长精确关键词、专有名词、作者名、术语匹配；FAISS 向量检索擅长词面不同但语义相近的表达。学术引用里两类需求都存在，因此组合使用比单一方案更稳。

**追问：向量检索一定更好吗？**  **答**：不一定。语义相似可能只表示主题接近，不等于支持当前具体主张；准确术语和数据集名称往往需要关键词检索补强。

## 7. Rerank 放在哪一层，为什么不能只加大 top-k？

**答案**：Rerank 放在 BM25/FAISS 初步召回和最终证据组装之间，对较小候选集按“当前主张与段落是否真正相关/支持”做精排。只加大 top-k 会把更多噪声交给后续模型，增加成本并降低证据聚焦；Rerank 是提高候选精度，不能替代召回。

**追问：Rerank 的代价？**  **答**：会增加时延和成本，也依赖候选集包含正确证据；因此需通过指标评估收益，而不是默认越复杂越好。

## 8. 什么是 Hybrid RAG，为什么更稳？

**答案**：Hybrid RAG 将词法召回和语义召回结合，再进行重排。它同时覆盖术语精确匹配与语义改写场景，减少单路检索的漏召回或误召回；但要承担索引、融合、调参和评测复杂度。

**追问：如何证明“更稳”？**  **答**：在固定人工标注集上对比 Recall@k、证据覆盖率和判定准确率，并分析错误 case；没有对比数据就只说设计动机，不说效果结论。

## 9. Recall@k 是什么？

**答案**：它衡量人工认定的正确证据是否出现在前 k 个检索候选中。它主要反映召回层的覆盖能力；正确证据没进入候选，后续重排和判定无法补救。

**追问：Recall@k 高是否代表最终判断准确？**  **答**：不代表。候选里有正确段落不等于系统最终选中了它，也不等于模型正确理解了证据。

## 10. 什么是证据覆盖率？

**答案**：它关注最终提供的证据是否覆盖人工认定支撑该引用主张所需的关键信息。它比“召回到相关段落”更接近证据是否充分，但仍不同于最终分类是否正确。

**追问：与判定准确率的区别？**  **答**：证据覆盖率看“给出的依据够不够”，判定准确率看“最终结论对不对”；两者可能一高一低。

## 11. 判定准确率衡量什么？

**答案**：它比较系统的结构化判断与人工标注标签是否一致，衡量端到端输出。需要与标签定义、无法确认政策和人工标注一致性一起解释，不能脱离数据集单独看。

**追问：标签本身不一致怎么办？**  **答**：先明确标注指南、正反例和争议处理；必要时双人标注、讨论或记录分歧。否则模型准确率没有稳定参照。

## 12. 如何构建人工标注集并避免数据泄漏？

**答案**：每个 case 包含引用上下文、目标文献、关键证据位置、标签和理由；按论文、引用对或时间做集合划分，避免同一引用对的改写或高度相似段落同时出现在调参和测试集中，并冻结最终测试集。

**追问：当前项目是否已采用上述完整划分？**  **答**：当前简历只确认使用人工标注集和三个指标，具体划分方法需要查项目记录；面试中可作为严谨的评测设计说明，而不说成已完成事实。

## 13. 证据不足时为什么返回“无法确认”？

**答案**：检索不到充分证据可能来自 PDF 解析失败、表格未解析、查询构造不足、索引覆盖有限或原文本就没有相关信息。把它直接判为不支持会把系统能力边界误当成事实；返回无法确认能保留不确定性并提示下一步人工核查。

**追问：这会不会让系统太保守？**  **答**：保守是高风险证据判断中的必要边界。可以通过改善解析、召回和证据覆盖降低无法确认比例，但不能靠放宽标准伪造确定性。

## 14. 给一个“无法确认”的具体例子。

**答案**：引用句说某方法在特定数据集显著优于基线，但检索到的只有方法介绍，没有实验表格或结论段。此时系统应指出缺少可定位的结果证据，返回无法确认并建议查看表格、附录或原始 PDF，而不是根据常识猜测。

**追问：如果模型认为语义上很像支持怎么办？**  **答**：语义相似不是充分证据；要求模型只基于可定位片段输出理由，缺少关键实验信息仍必须降级。

## 15. PDF 是扫描件、解析错乱或没有参考文献怎么办？

**答案**：把这些作为输入质量问题显式返回：扫描件可能需要 OCR 或人工查看，解析错乱不能保证段落和来源定位可靠，没有参考文献则无法建立完整引用关联。系统不能静默继续给出确定结论。

**追问：这些能力都已实现了吗？**  **答**：当前简历确认了 GROBID 解析和异常处理，OCR、表格解析等具体能力需核实；只能作为后续完善方向。

## 16. Redis 在该项目中适合缓存什么？

**答案**：适合缓存可复用且版本稳定的中间结果，例如同一 PDF 的解析结果或相同检索请求的候选结果，以减少重复解析和检索。缓存 key 应包含文档版本、解析/索引版本和查询相关信息；具体 key、TTL 和失效策略以实际实现为准。

**追问：为什么不能永久缓存？**  **答**：PDF、解析器、索引、模型或切分策略更新后旧结果会过时，因此需要版本标识和失效策略。

## 17. FastAPI、Docker、日志的工程作用分别是什么？

**答案**：FastAPI 提供请求校验和服务接口；Docker 固化 GROBID 等依赖及运行环境；日志帮助定位 PDF 解析、检索和判定阶段的异常。三者共同让原型链路更容易部署、复现和排障，但不等于我已完成大规模线上运维。

**追问：接口如何设计长耗时任务？**  **答**：可采用提交任务返回 ID、查询进度/结果、记录失败原因的模式；这是通用工程设计，需要与该项目实际接口实现区分。

## 18. 如何根据评测集选择改检索、重排还是提示词？

**答案**：先看错误处在哪一层：正确证据没进 top-k，优先查 query、切分、元数据和召回；候选有正确证据但排序靠后，查 Rerank；证据充分却判错，查标签定义、结构化输出与提示约束。每次只改一个主要假设，再在固定集上比较，不凭主观调参。

**追问：能同时改很多项再看结果吗？**  **答**：可以做探索，但无法归因；要形成工程结论，关键实验应控制变量或至少记录变更组合与对应结果。

## 19. 发现误判后如何保留 case 并防止回归？

**答案**：保存脱敏的 case 标识、引用上下文、目标文献、人工证据位置、错误类型、系统版本和人工修订理由；把代表性 case 放入回归集。修改解析、检索、重排或判定后，重新运行固定 case，确认同类错误没有反复出现。

**追问：这是当前已完成的平台吗？**  **答**：不是。当前已确认的是人工标注集和指标评估；固定回归集、版本对比与反馈回流是我会继续完善的工程方案。

## 20. 这个项目与你前两个 Agent 项目有什么共通方法？

**答案**：共通点是把模型放在受控证据和工程边界内。质量 Agent 让结构化指标和 RAG 依据各归其位；评审 Agent 用固定 SHA 和证据链约束裁决；论文引用查证 Agent 用解析、检索、来源证据和无法确认约束判断。三者都不把 LLM 的自然语言输出直接当成最终事实。

**追问：最大的不同是什么？**  **答**：质量 Agent 侧重企业结构化业务数据和工具调用，评审 Agent 侧重仓库快照与任务状态，论文项目侧重长文档解析、检索质量和评测闭环。

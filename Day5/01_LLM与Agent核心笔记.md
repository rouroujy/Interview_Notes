# LLM 与 Agent 核心笔记：从概念到工程取舍

> **复习原则**：每个概念都回答四件事——它是什么、工程上影响什么、替代方案是什么、在我的项目里如何体现。

---

## 一、LLM 基础：面试够用的工程解释

### 1. Transformer 与自注意力

> Transformer 是以注意力机制为核心的序列建模架构。自注意力让一个 token 在处理时根据其他 token 的相关性聚合信息，因此更擅长理解长距离关系；但注意力计算和上下文长度带来成本与延迟压力。对 AI 应用工程师而言，重点不是推导公式，而是理解：模型并不天然“知道业务事实”，它只是基于输入上下文生成下一个 token，因此需要用检索、工具、结构化输入和验证来约束它。

**项目映射**：质量 Agent 不让模型凭记忆统计 Bug；论文项目不让模型凭印象判断引用；评审 Agent 不让模型自由编造路径和行号。

### 2. Token 与上下文窗口

> Token 是模型处理文本的基本单位，不等于一个汉字或英文单词。上下文窗口限制一次可输入、输出和保留的 token 总量；窗口变大不等于应该塞入全部材料，因为噪声、成本、注意力分散和敏感信息暴露也会增加。

**项目映射**：Harness 先选任务单、决策、接口契约、测试计划和相关代码，而非把完整仓库塞给 AI；论文项目先检索证据而非让模型直接读全文。

### 3. Temperature 与 Top-p

| 参数 | 直观作用 | 工程取舍 |
| --- | --- | --- |
| `temperature` | 调整候选 token 分布的随机性 | 越低通常越稳定、可复现；越高更发散，适合创意但增加格式和事实风险 |
| `top-p` | 只在累计概率达到 p 的候选集合中采样 | 可限制长尾候选，和 temperature 联合影响多样性 |

**项目口述**：当前工程的部分受控任务使用 `temperature=0`，例如代码评审 LLM 工厂与质量 Agent 默认调用，目的是降低意图分类、结构化裁决等任务的随机性；但它不能保证事实正确，也不能替代 schema 校验、证据校验或测试。

### 4. 系统提示词、用户提示词与上下文

- **系统提示词**：角色、硬约束、输出边界和安全规则。
- **用户提示词**：本次任务目标和输入。
- **上下文/证据**：RAG 检索结果、工具返回、任务单、接口契约等可用事实。

> 高质量 Prompt 不是长篇角色扮演，而是明确任务、允许使用的事实、禁止行为、输出 schema、拒答条件和例子。

## 二、Agent 与 Workflow：先选可控形态

### 1. 四种常见范式

| 范式 | 特征 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| Workflow | 节点和路径基本固定 | 规则明确、审计要求高的企业流程 | 灵活性较低，新增分支需显式设计 |
| ReAct | 模型交替推理和调用工具 | 探索性查询、工具集合有限的问题 | 工具误用、循环、过程不可控 |
| Plan-and-Execute | 先生成计划，再逐步执行 | 长任务、多子目标 | 计划可能过期，执行偏离计划 |
| Multi-Agent | 多个角色分工协作 | 专业边界清晰且单 Agent 难以覆盖 | 通信成本、上下文重复、责任不清、失控 |

### 2. 我的项目为什么更偏 Workflow

> 我的企业质量 Agent 更偏固定 Workflow：质量问题先进行意图识别，再调用允许的指标工具，最后格式化结果；当前图是明确的线性节点，而不是让模型自由规划数据库查询。成果评审 Agent 同样把快照、事实提取、证据组装、裁决和人工确认拆成受控阶段。原因是这些场景有明确数据边界、权限、审计和人工责任要求，优先级是可验证和可维护，而不是最大化自主性。

### 3. LangGraph 的价值与边界

| 相比方式 | LangGraph 的价值 | 仍需自己解决 |
| --- | --- | --- |
| 普通链式调用 | 显式状态、节点、边和条件分支，更易观察和测试 | 节点职责、数据模型、工具权限与异常策略 |
| `while` 循环自由 Agent | 可限制迁移路径、增加中断/人审/恢复节点 | 图设计不好仍会复杂、状态膨胀 |
| 复杂 Agent Runtime | 适合现有业务流程的轻量编排，不必引入大而全自治框架 | 不自动提供正确的业务规则或评测体系 |

## 三、工具调用、Schema 与验证

### 1. 函数调用、ToolRegistry、MCP 的关系

| 概念 | 含义 | 项目关系 |
| --- | --- | --- |
| 函数/工具调用 | 模型以结构化参数请求调用某个能力 | 质量 Agent 通过工具查询受控指标 |
| ToolRegistry | 应用内注册、发现、参数校验和审计工具的机制 | 当前项目用于隔离 Agent 与 DB/API |
| MCP | 让模型客户端与外部工具/资源服务通信的开放协议 | 可作为后续适配边界，但不是当前 MVP 主链路 |

> 三者不冲突：函数调用是模型层的调用形式，ToolRegistry 是应用内治理层，MCP 是跨客户端/服务的协议层。企业 MVP 先解决业务模型、权限、审计和测试，再判断是否需要引入 MCP。

### 2. 结构化输出的可靠链路

```text
任务定义 + 输出 schema + 少量正反例
        ↓
LLM 尝试返回 JSON / tool arguments
        ↓
服务端解析 JSON
        ↓
Pydantic 类型/格式校验
        ↓
业务校验（枚举、时间、范围、状态迁移）
        ↓
权限/证据校验
        ↓
执行、降级或请求人工确认
```

**项目事实**：质量 Agent 的意图分类 prompt 要求只返回 JSON；服务端会处理代码块、前后文字和非 JSON 异常。需求变更标注也需要解析结构化字段，异常时走保守结果，而不是把无效文本直接写入业务结论。

### 3. 为什么“符合 Pydantic schema”仍不够

> Pydantic 能校验类型、必填字段和基础格式，但不能保证业务正确。例如日期格式合法不代表时间范围合理，模块名存在不代表属于当前项目，模型给出的证据字符串也不代表真实存在。因此还要做业务校验、权限校验和证据/来源校验。

## 四、Prompt Engineering 与 Context Engineering

### Prompt 的最小结构

1. 任务：要完成什么，成功标准是什么。
2. 事实范围：可使用哪些文档、工具结果和字段。
3. 约束：禁止编造、禁止越权、证据不足时怎么做。
4. 输出：JSON schema、字段解释、示例和错误处理。
5. 验证：服务端如何解析、校验和降级。

### Context Engineering 的选择顺序

> 先固定任务边界和版本，再提供稳定约束（任务单、决策记录、接口契约、测试计划），最后按需检索相关代码、RAG 证据或工具结果。信息不足时继续检索或交给人工，不让模型补全猜测。

**项目映射**：Harness 是仓库级 Context Engineering；论文项目用 Hybrid RAG 为引用判断选择证据；评审 Agent 用固定 SHA 和候选证据约束评审上下文。

## 五、常见失败模式与控制层

| 失败模式 | 发生原因 | 控制层 |
| --- | --- | --- |
| 幻觉 | 模型将概率生成当事实 | RAG/工具事实、来源引用、无法确认、人审 |
| 工具误用 | 工具描述模糊、参数未校验、权限过大 | ToolRegistry、schema、白名单、权限校验、审计 |
| 循环调用 | 自由 Agent 没有终止条件或预算 | 固定图、最大步数/超时、状态检查、人工中断 |
| 上下文膨胀 | 全量材料堆入 prompt | 任务边界、检索、摘要、版本化上下文 |
| Prompt Injection | 不可信内容试图改写指令/诱导工具 | 指令与数据分离、工具最小权限、服务端授权、输出验证 |
| JSON 解析失败 | 模型加解释、代码块、字段缺失或格式错误 | 原始输出解析、Pydantic 校验、重试/修复、保守降级 |

## 六、模型选型：没有压测数据时怎么回答

> 我不会直接说某个模型“最好”或“最省钱”。我会先按任务拆分：结构化分类、RAG 重排、长文归纳、代码事实提取对能力要求不同；再定义离线 case 和验收指标，例如 JSON 合法率、工具选择正确率、证据引用合法率、判定一致性、P95 时延和单任务成本；然后比较候选模型在固定任务、固定上下文和固定参数下的质量、稳定性、时延、成本、隐私与可用性。没有实际实验数据时，我只说明这个选型框架，不把它说成已有对比结论。

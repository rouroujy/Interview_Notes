## 一、当天在十天计划中的位置

Day 2–Day 4 已经通过质量 Agent、成果评审 Agent、AI Coding Harness 和论文引用查证 Agent 展示了具体项目。Day 5 把这些项目背后的共通基础抽出来：LLM 如何生成、工作流与 Agent 如何取舍、Prompt/Schema/工具如何约束输出、上下文如何选择，以及如何处理幻觉、注入和结构化输出失败。

今天的重点不是把自己包装成模型训练工程师，而是能以 AI 应用工程师的视角说明：**模型能力有边界，交付质量来自任务拆分、上下文、工具约束、验证与人工责任的组合。**

## 三、已确认事实与不可扩展边界

### 已确认的实现事实

- 质量 Agent 当前采用固定的 LangGraph 线性图：意图分类 → ToolRegistry 工具调用 → 回复格式化。
- Agent 节点不应直连数据库或禅道 API，而是通过 ToolRegistry 访问受控能力。
- 意图分类提示词要求 JSON 输出；服务端会解析 JSON，并对模型异常/格式异常走错误或降级路径。
- 代码评审模块使用独立的 LLM 实例，设置 `temperature=0`、请求 timeout 和最多 5 次重试；任务层还设置阶段 deadline 与协作式取消。
- 需求变更标注等自然语言任务使用结构化字段和证据落库复用；解析失败或 LLM 异常不会被当作确定业务事实。

### 不可擅自扩展的事实

- 未确认具体模型对比、线上成本、延迟、吞吐、token 消耗、A/B 实验或 Prompt 版本平台，不写具体数值。
- MCP 不是当前质量 Agent MVP 主链路；可以讲它与函数调用/工具协议的关系，但不说项目已通过 MCP 接入。
- 复杂多 Agent、自治规划、长期记忆、自动巡检不属于当前 MVP 已确认主线。

## 四、当天能力目标

- 能解释 Transformer、自注意力、Token、上下文窗口、温度、Top-p、系统提示词和结构化输出的工程影响。
- 能区分 Workflow、ReAct、Plan-and-Execute、Multi-Agent，且说明自己的项目为什么更偏受控 Workflow。
- 能解释 LangGraph 相比普通链式调用或自由循环的价值与成本。
- 能说明函数调用、ToolRegistry 和 MCP 的关系及边界。
- 能回答如何让模型稳定输出 Pydantic schema 的 JSON、如何处理解析失败。
- 能说明 Prompt Injection、工具误用、上下文膨胀、循环调用和幻觉的防护思路。
- 能从任务、上下文、工具、评测四个角度设计一个可交付的 AI Coding Agent。
- 能在没有实际压测数据时，严谨说明模型选型方法而不虚构结论。

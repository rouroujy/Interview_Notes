# Day 5：30 分钟复习版——LLM、Prompt 与 Agent 基础

> **目标**：不背教材定义，只能用项目语言回答：模型为什么需要上下文、工具、验证和人审。

## 0–5 分钟：90 秒主线口述

> 我理解的 Agent 不是“模型自己决定一切”，而是把模型放到受控工作流中：先根据任务选择相关上下文，再通过受限工具获得事实，模型负责理解和归纳，服务端负责 schema、业务、权限和证据校验，信息不足时降级或交给人工。我的质量 Agent 是固定 LangGraph 线性 Workflow，意图分类后通过 ToolRegistry 调用指标工具；论文项目用 RAG 提供可定位证据；评审 Agent 用固定 SHA 和证据校验；Harness 用任务单、决策、契约和测试限制 AI Coding 的边界。

**事实边界**：当前已确认受控 Workflow、ToolRegistry、JSON 解析、部分 `temperature=0`、评审调用 timeout/retry；未确认模型压测、成本对比、MCP 接入或复杂多 Agent 实践。

## 5–12 分钟：白板关键词链

```text
用户请求
→ 任务/上下文边界
→ Workflow（意图 → 工具 → 证据/规则 → 输出）
→ JSON/Pydantic 校验
→ 业务/权限/证据校验
→ 回答 / 无法确认 / 人工确认
→ 审计、测试 case、反馈
```

### 三句必说

1. “LLM 的输出是概率生成，不是业务事实；事实要来自工具、RAG 原文或固定证据。”
2. “Prompt 要求 JSON 不等于输出可执行；服务端仍要做 schema、业务和权限校验。”
3. “temperature=0 降低随机性，不等于不会幻觉。”

## 12–20 分钟：8 个必答题

### 1. Workflow 与 Agent 的区别？

> Workflow 路径固定、可控；Agent 更强调模型根据环境选择动作。我的项目更偏 Workflow，因为企业场景需要审计、权限和人审。

### 2. 什么时候不该用 Agent？

> 规则可完全确定、普通 CRUD/报表就能完成、错误成本很高且没有验证闭环时，不应为了 AI 而引入 Agent。

### 3. ToolRegistry、函数调用、MCP 的关系？

> 函数调用是模型表达工具参数的形式，ToolRegistry 是应用内的治理层，MCP 是跨客户端和服务的协议层；当前项目主线是 ToolRegistry，不是 MCP。

### 4. 为什么 LangGraph？

> 节点、状态和边显式，方便限制路径、测试、追踪和人审；但图本身不替代业务规则和权限设计。

### 5. 如何稳定输出 JSON？

> Prompt schema + 解析 + Pydantic + 业务/权限/证据校验；异常不直接执行，走重试、降级或人工确认。

### 6. 如何防 Prompt Injection？

> 区分指令和不可信数据，工具最小权限，服务端授权，输出验证，高风险动作人审；不能只靠模型“识别攻击”。

### 7. 长上下文、RAG、摘要记忆如何选？

> 有限整体材料用长上下文；大规模/更新知识用 RAG；长会话压缩用摘要，但高风险事实要回原文或工具。

### 8. 模型如何选？

> 按任务和固定 case 比质量、稳定性、时延、成本、隐私与可用性；没有压测数据只讲方法，不下结论。

## 20–27 分钟：四个失败模式

| 风险 | 一句话控制 |
| --- | --- |
| 幻觉 | 来源证据、工具事实、无法确认、人审。 |
| 工具误用 | 白名单、schema、业务权限校验、审计。 |
| JSON 失败 | 解析/Pydantic/降级，不能直接执行原文。 |
| 上下文膨胀/注入 | 任务边界、相关检索、数据与指令分离、最小权限。 |

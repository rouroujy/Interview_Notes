# Day 5：LLM 与 Agent 高频问答

> 共 40 题。每题按“定义 → 工程影响 → 项目映射或个人边界”口述；不要把通用概念说成未验证的线上项目事实。

---

## 1. 什么是 LLM？

**答案**：LLM 是基于大量文本训练、根据上下文预测后续 token 的语言模型。工程上它擅长理解、归纳、生成和把自然语言转成结构化候选，但不能天然保证事实、权限或业务规则正确。我的项目中让 LLM 做意图识别、需求变更语义标注、证据归纳，而把指标、权限和来源校验放到工具和服务端。

## 2. 什么是 Token？

**答案**：Token 是模型处理文本的基本单位，不严格等于汉字或单词。它影响输入输出上限、成本、时延和截断风险。项目里不应因为窗口变大就输入完整仓库或整篇论文，而要选择任务相关的上下文和证据。

## 3. 什么是上下文窗口？

**答案**：上下文窗口是一次调用可处理的输入和输出 token 总量。窗口不足会截断，窗口过度使用会增加成本和噪声；Harness 因此选择任务单、决策、契约、测试和相关代码，论文项目用 RAG 找证据。

## 4. Transformer 的工程意义是什么？

**答案**：Transformer 通过自注意力建模 token 间关系，能处理复杂语义和长距离依赖。工程上仍要认识到注意力不是事实验证：模型会根据上下文概率生成，因此需要检索、工具、schema 和人工确认。

## 5. 自注意力是什么？

**答案**：自注意力让当前 token 根据其他 token 的相关性聚合信息。它解释了模型为何能关联远距离文本，也解释了长上下文中噪声和无关信息会影响输出；因此 Context Engineering 需要筛选而非堆料。

## 6. `temperature` 是什么？

**答案**：它控制采样随机性。低温度通常更稳定，适合分类、JSON 和裁决；高温度更发散，适合创意候选。当前代码中部分受控调用使用 `temperature=0`，但这只能降低随机性，不能保证不幻觉。

## 7. `top-p` 是什么？

**答案**：`top-p` 只从累计概率达到阈值的候选集合中采样，用于限制低概率长尾 token。它与 temperature 都影响多样性和稳定性；没有实际实验数据时，我不会说某个取值最优。

## 8. 系统提示词和用户提示词分别做什么？

**答案**：系统提示词定义角色、硬约束和安全边界，用户提示词提供本次请求。两者都不能替代服务端授权；不可信用户文本或检索文本不能覆盖系统规则。

## 9. 什么是 Prompt Engineering？

**答案**：它是把任务、事实范围、约束、输出格式和降级条件明确表达给模型的方法。项目中意图分类 prompt 限制可选工具并要求 JSON；但 Prompt 只是第一层，还需解析、schema、业务和权限校验。

## 10. 什么是 Context Engineering？

**答案**：它是为某个任务选择、组织和版本化有效上下文，而不是简单扩大 prompt。Harness 用任务单、决策记录、接口契约和测试计划；评审 Agent 用固定 SHA 和候选证据；论文项目用 Hybrid RAG。

## 11. 什么是结构化输出？

**答案**：让模型按 JSON 或 schema 返回字段化结果，而非自由文本。它便于程序调用、测试、审计和降级；当前质量 Agent 的意图分类要求 JSON，需求变更标注也解析结构化字段。

## 12. 如何让模型更稳定输出 Pydantic JSON？

**答案**：先给清晰 schema、枚举、字段描述和只输出 JSON 约束，必要时给例子；然后服务端解析代码块/前后文本，用 Pydantic 做类型校验，再做业务、权限和证据校验。失败时重试、降级或人工确认，不能直接执行原文。

## 13. Pydantic 校验是否足够？

**答案**：不够。它主要验证类型和格式；例如日期合法不等于范围合理，工具名合法不等于调用者有权限，引用字段存在不等于证据真实。因此还要有业务、权限和来源校验。

## 14. 模型返回 JSON 代码块怎么办？

**答案**：解析层应先剥离代码块或前后说明，再解析对象并校验 schema。当前项目代码对这类输出有兼容处理；但解析成功不代表业务正确，后续校验不能省。

## 15. 模型输出非 JSON 或字段缺失怎么办？

**答案**：视任务风险处理：不能将自由文本当作结构化指令执行；低风险任务可有限重试或格式修复，高风险任务应降级或人工确认，并保留失败 case 用于测试。

## 16. 什么是函数/工具调用？

**答案**：模型用结构化参数请求应用执行某个预定义能力，例如查询指标或读取受限资源。模型负责提出候选调用，应用负责验证参数、权限和执行结果；不能把工具调用当作模型直接拥有系统权限。

## 17. ToolRegistry 的作用是什么？

**答案**：它集中管理工具注册、发现、参数约束和调用边界，使 Agent 不直接访问数据库或外部 API。质量 Agent 用它隔离指标查询与底层系统，便于审计、测试和扩展。

## 18. MCP 与函数调用、ToolRegistry 的关系？

**答案**：函数调用是模型表达调用参数的形式，ToolRegistry 是应用内治理机制，MCP 是模型客户端与外部工具/资源服务通信的协议。当前项目 MVP 主链路是 ToolRegistry，不应说已用 MCP 接入。

## 19. 什么是 Agent？

**答案**：Agent 通常指能根据任务、上下文和工具选择动作并推进任务的系统。工程上要明确自主性范围、可用工具、终止条件和责任边界；我的项目更强调受控工作流而不是开放式自治。

## 20. Workflow 与 Agent 有什么区别？

**答案**：Workflow 的节点和路径由程序明确设计，Agent 更强调模型动态选择动作。两者可结合，但企业系统常先用 Workflow 获得可控性；质量 Agent 当前是固定线性图。

## 21. 为什么项目选择 LangGraph？

**答案**：LangGraph 将状态、节点和边显式化，适合组织工具调用、异常分支、人审和可测试路径。质量 Agent 用它串联意图、工具和回复；评审 Agent 用它组织受控分析阶段。

## 22. LangGraph 相比普通链式调用有什么优势？

**答案**：普通链适合简单一次性顺序任务；图能显式表达状态更新、条件迁移、循环、中断和恢复，更适合长任务或有人审的过程。代价是状态模型和图设计更复杂。

## 23. 什么时候不应该使用 Agent？

**答案**：规则能完全确定、普通 CRUD/报表即可解决、错误代价极高且无法验证、数据和权限未明确时，不应为了 AI 而引入 Agent。先用确定性程序通常更简单可靠。

## 24. 什么是 ReAct？

**答案**：ReAct 是模型在推理与工具行动之间交替的模式，适合探索性问题。风险是工具误用、循环和过程难以审计；企业质量主链路没有把它作为默认形态，而是固定允许的步骤。

## 25. 什么是 Plan-and-Execute？

**答案**：先让模型生成任务计划，再逐步执行。它适合多步骤目标，但计划可能过期、执行环境可能变化，因此要检查计划、限制动作并允许重规划；当前项目没有把它作为已实现主线。

## 26. 什么是 Multi-Agent？

**答案**：多个 Agent 按角色协作完成任务，例如检索、分析、审查分工。它只有在专业边界清晰、协作收益大于通信成本时才值得采用；否则上下文复制、责任不清和调试成本会更高。

## 27. 为什么你的项目不优先做复杂多 Agent？

**答案**：当前质量与评审问题的主路径、工具和人工确认点都明确。先用单主 Workflow 跑通数据、规则、证据和审计，能更容易验证；复杂多 Agent 是后续可评估方向，而不是为了技术名词而引入。

## 28. 什么是 Human-in-the-loop？

**答案**：在高风险、不确定或需要业务责任的节点让人参与确认、修改或终止。评审 Agent 只生成草稿，人工确认后归档；Harness 在任务范围和验收保留人工决定；证据不足时交给人核查。

## 29. 什么是 RAG？

**答案**：RAG 在生成前检索相关外部材料并提供给模型，使回答更基于可更新来源。它适合制度、文档和论文证据；不适合代替结构化数据库做精确统计。

## 30. 为什么 RAG 仍会幻觉？

**答案**：检索可能漏召回、召回无关内容、chunk 丢上下文，模型也可能忽略证据或过度推断。因此要保留来源、元数据过滤、重排、证据校验和无法确认；论文项目和质量 Agent 都体现了这一边界。

## 31. 长上下文、RAG、摘要记忆如何选择？

**答案**：有限且需要整体比对的材料可用长上下文；大规模或持续更新知识适合 RAG；长会话历史可用摘要记忆。摘要会丢细节，高风险事实仍要回原文、工具或固定证据。

## 32. 什么是 Prompt Injection？

**答案**：不可信输入试图诱导模型忽略约束、泄露信息或调用越权工具。防护不能只靠提示词，要分离指令和数据、限制工具权限、服务端授权、校验输出并对高风险动作人审。

## 33. RAG 文档中出现“忽略规则”怎么办？

**答案**：把检索文档当数据而非高优先级指令，提示词明确其可信级别；同时模型不能因此获得额外工具权限，服务端仍按白名单和身份授权执行。必要时标记/过滤异常内容并记录 case。

## 34. 什么是工具误用，如何防止？

**答案**：模型选择了不该用的工具、给出超范围参数或误解了返回结果。用清晰工具描述、schema、枚举白名单、业务/权限校验、最小权限和审计控制；质量 Agent 不允许模型直接拼 SQL。

## 35. 什么是循环调用，如何处理？

**答案**：Agent 反复调用工具却无法结束。可以通过固定图路径、最大步数/预算、超时、状态检查、幂等和人工中断控制；评审任务还使用阶段 deadline 与协作式取消。

## 36. 什么是幻觉？

**答案**：模型生成看似合理但无事实依据、错误或不可验证的信息。降低它不是只换大模型，而是让结构化事实由工具计算、文档问题有来源证据、输出经校验，证据不足时明确降级。

## 37. 如何设计一个可靠的 AI Coding Agent？

**答案**：从四方面设计：任务上明确目标、范围和验收；上下文上提供任务单、决策、契约、测试和相关代码；工具上限制读写权限与命令边界；评测上使用测试、代码审查、证据与失败 case。Harness 和评审 Agent 分别覆盖开发约束与成果审查。

## 38. 模型选型看哪些维度？

**答案**：按具体任务看质量、结构化稳定性、工具选择、证据引用、时延、成本、隐私、可用性和运维兼容性。应使用固定 case、固定上下文和指标比较；没有真实实验数据时只讲框架，不说某模型已经最优。

## 39. 为什么不能只靠换更大模型？

**答案**：许多失败来自任务不清、数据错误、权限缺失、检索漏召回或输出未验证，换模型无法修复系统边界。先定位失败层，再选择改上下文、工具、检索、提示约束或模型。

## 40. 如何评估一个 Agent 是否可交付？

**答案**：至少看任务成功/失败定义、工具调用正确性、结构化输出合法率、来源/证据质量、异常降级、人审流程、时延成本和回归 case。我的项目已体现受控工具、证据、任务状态和人工确认；完整线上 AgentOps 指标平台仍需按实际经历区分。

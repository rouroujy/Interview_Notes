## 一、白板题：设计一个受控企业 Agent

### 画图要求（5 分钟）

```text
用户请求
  ↓
输入校验 / 身份权限
  ↓
受控上下文：任务规则 + RAG 证据 + 工具结果
  ↓
LangGraph Workflow：意图 → 工具 → 规则/证据 → 输出
  ↓
JSON/schema 校验 + 业务/证据校验
  ↓
回答 / 无法确认 / 人工确认
  ↓
审计、测试 case、反馈迭代
```

### 必须解释的三点

1. 为什么模型不能直接访问数据库或任意外部 API。
2. 为什么 JSON schema 校验后还要做业务、权限和证据校验。
3. 为什么“无法确认”和人工确认是功能，不是失败。

## 二、90 秒压力回答

### 题目：你的项目为什么不用复杂多 Agent？

> 当前项目的主要问题是企业质量分析和受控评审，数据源、规则、工具和人工确认点都比较明确。此时优先用单主 Workflow，把意图、工具、证据和状态拆成固定节点，收益是可测试、可审计和可维护。多 Agent 只有在任务确实需要稳定的专业分工、单 Agent 上下文过载且协作收益大于通信成本时才考虑；否则会增加调试、责任边界和成本。我不会为了显得先进而把多 Agent 当成默认方案。

### 题目：如何让模型稳定返回 Pydantic JSON？

> 先用 Prompt 明确 schema、枚举和只输出 JSON，必要时给例子；然后服务端解析原始内容，处理代码块或多余说明；再用 Pydantic 做类型格式校验，最后做业务、权限和证据校验。解析失败不能直接执行，应重试、降级或人工确认。当前项目意图分类和需求变更标注都有“模型输出后仍需程序解析与保守处理”的设计。

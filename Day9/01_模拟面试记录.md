## 二、模拟一：Agent / AI Coding 技术面（建议 45–55 分钟）

**规则**：先做 90 秒开场；每题 90 秒，追问 30–60 秒。面试官可随机连续追问，不允许跳题。

### 1. 请介绍你当前最有代表性的 Agent 项目。

**参考落点**：优先选成果评审 Agent 或质量管理体系 Agent。按业务痛点、受控流程、事实/证据边界、人工确认和可观测性展开；不要把两者混为一个系统。

### 2. 成果评审 Agent 为什么需要 9 节点 LangGraph 工作流，而不是一次 Prompt？

**参考落点**：清单加载、快照、目录/依赖解析、事实提取、证据组装、逐项裁决各有输入输出和失败边界；节点化便于审计、重试、进度和人工确认。不是因为“LangGraph 天然更智能”。

### 3. 你如何避免 LLM 对代码合规性做无依据判断？

**参考落点**：每项结论关联文件路径、行号和快照 SHA；校验 LLM 输出中的证据索引，证据缺失或引用非法则降级为“无法确认”，由人工确认归档。

### 4. 质量管理体系 Agent 中，结构化指标、RAG 和 LLM 分别做什么？

**参考落点**：指标引擎计算 BUG 严重等级、功能分布、激活、需求变更等；RAG 检索质量体系 checklist；LLM 负责归纳、解释和受控工具编排。不能让模型凭空计算或替代规则事实。

### 5. ToolRegistry 的价值是什么？工具可以让模型任意调用吗？

**参考落点**：收敛数据访问路径，统一参数校验、权限、审计和测试；工具有白名单、输入 schema、范围和结果格式。高风险写操作不能由模型自行越权。

### 6. 质量 Agent 为什么采用 Edge 主动同步？如何保证可靠？

**参考落点**：中心系统无法主动访问分公司内网 GitLab，因此 Edge 在内网侧读取后向中心同步，缩小跨网访问面；SQLite Outbox 持久化待发送批次、游标增量减少全量、批次稳定标识支持中心幂等。语义是至少一次投递下去重，不承诺恰好一次。

### 7. 评审任务为什么要做状态机？取消和服务重启怎么处理？

**参考落点**：任务覆盖创建、执行、待人工确认、取消、失败与中断；创建可用幂等键避免重复任务，取消请求由安全检查点协作消费，重启遗留活动任务标记为 `interrupted` 并由人工决定重试。不要说实现了通用断点续跑。

### 8. 你如何评估 Agent 是否真的可靠？

**参考落点**：先定义任务级正确性，如 checklist 覆盖、证据可定位、非法引用率、人工确认修改率、失败/超时分布；评测集要覆盖正常、缺证据、解析失败和边界输入。当前已确认“论文引用查证”使用人工标注集和 Recall@k、证据覆盖率、判定准确率；其他项目不能虚构具体线上指标。

### 9. 请解释 AI Coding Harness 的 Context Engineering。

**参考落点**：不是堆上下文，而是把架构约束、接口契约、测试策略、稳定决策和任务状态沉淀为 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等可检索、可更新的协作物；流程是业务建模→任务单人工确认→AI 编码与测试→人审验收→归档续接。

### 10. AI Coding Harness 如何保证 AI 不越权？

**参考落点**：关键业务责任由人工确认，任务单先审，接口契约和测试计划限制变更范围，代码和测试结果经人审验收后归档；它是受控开发框架，不是让模型自动完成并上线。

### 11. 如果 GitLab、LLM 或解析服务超时，系统如何设计？

**参考落点**：外部调用设置 timeout，任务按阶段记录错误和进度；有界并发与文件大小限制保护资源，失败进入稳定状态并保留可排障信息，必要时由人工重试。具体重试次数和退避参数以代码配置为准。

### 12. 面对“你为什么不用多 Agent / MCP / 向量库”的追问，如何回答？

**参考落点**：从问题复杂度和风险出发：确定性指标或受限数据访问优先工具/规则；需要文档依据时才引入 RAG；子任务确有独立目标和协作收益才拆多 Agent。MCP 是工具互操作协议选择，不等于项目一定采用；向量库也不是所有问题的默认方案。

## 三、模拟二：AI 全栈技术面（建议 40–50 分钟）

### 1. 请用 90 秒介绍轻舟货运飞船前端项目。

**参考落点**：Vue3 地面站遥测监控和货物辅助管理；遥测趋势、摄像机预览、灯光控制、报警监控、货架和操作记录；说明周期刷新、事件去重、用户操作暂停/恢复刷新、运行时配置。React 企业平台不是轻舟技术栈。

### 2. 为什么用户交互期间要暂停和恢复周期刷新？

**参考落点**：避免轮询回填覆盖用户正在编辑或选择的状态；进入交互锁定、保存/取消后刷新，必要时以版本或更新时间检测冲突。不是无限暂停，需保证恢复与超时兜底。

### 3. 轮询和 WebSocket 如何选择？

**参考落点**：低频、可容忍延迟且实现简单的状态查询可轮询；高频、强实时、多方订阅更适合 WebSocket，但要处理连接、鉴权、断线重连、背压和顺序。轻舟简历确认周期刷新，不声称已使用 WebSocket。

### 4. 前端事件去重、路由跳转和状态管理怎样协作？

**参考落点**：稳定事件 ID 防止同一报警重复弹窗/跳转；Vuex 放跨页面、共享且需要一致性的状态；Vue Router 负责把事件定位到具体页面。具体键、窗口和模块划分要以实际实现为准。

### 5. 运行时配置为什么比构建时写死后端地址更好？

**参考落点**：同一构建产物可按环境加载不同后端地址，减少为环境差异重复打包；配置需校验、提供默认/失败提示，敏感信息不能放到前端配置。

### 6. FastAPI 接口如何保证输入和错误输出清晰？

**参考落点**：Pydantic 做输入 schema 校验；业务层区分参数、权限、资源不存在、外部依赖和内部异常；返回稳定错误码/信息并记录可排障日志，避免把堆栈或敏感信息直接暴露给前端。

### 7. MySQL、SQLAlchemy、Alembic 在当前项目中各自解决什么问题？

**参考落点**：MySQL 持久化业务、任务和审计等结构化数据；SQLAlchemy 组织模型与事务访问；Alembic 管理 schema 迁移。表结构、索引与性能数字没有确认，不虚构。

### 8. Redis 在论文引用查证项目中适合缓存什么？缓存风险是什么？

**参考落点**：简历确认有 Redis 缓存，可复用成本高且可重建的解析或检索中间结果；需要 key 设计、TTL、失效和一致性策略。具体缓存对象与 TTL 未核实，不说已实现细节。

### 9. 为什么长任务不能一直占住 HTTP 请求？

**参考落点**：请求超时、连接资源和用户体验都会变差；创建接口快速返回任务 ID，后台执行，状态独立持久化，前端通过查询或推送查看进度。成果评审项目确认使用后台线程，不能说已用消息队列 worker。

### 10. 如何避免重复点击或网络重试导致重复创建任务？

**参考落点**：客户端防重复提交是第一层，服务端 `idempotency_key` 才是最终保障；同一幂等键返回同一任务/结果，并定义键的作用范围与生命周期。

### 11. Edge 同步中游标、Outbox 和中心幂等分别解决什么问题？

**参考落点**：游标确定增量范围；Outbox 先持久化待发批次再传输、便于失败重试；中心按批次标识去重，抵抗至少一次投递的重复。重叠窗口防漏，重复由幂等吸收。

### 12. 如果你要把当前 MVP 演进为更高并发的服务，先做什么？

**参考落点**：先以压测和观测确认瓶颈与目标，再做限流、队列/worker、容量隔离、缓存策略、数据库优化、超时/熔断和全链路追踪；当前事实是有界并发和基础状态管理，不把它说成完成了高并发平台。

## 四、模拟三：综合面（建议 35–45 分钟）

### 1. 为什么选择 AI 应用 / Agent / AI 全栈方向？

**参考落点**：从人工智能硕士课程、当前企业 Agent 实习、论文引用查证和前端项目形成的交叉能力讲起；目标是把模型能力做成可靠业务系统，不要泛泛说“行业热门”。

### 2. 请讲一次你推动复杂任务落地的经历。

**参考落点**：可选 Edge 主动同步或成果评审状态机。说明约束、你的设计/实现职责、协作对象、如何拆风险、结果和复盘；不把团队交付全部归为个人。

### 3. 项目中出现过意见不一致时，你如何处理？

**参考落点**：先对齐目标、事实和约束，再用小范围验证或文档记录决策；保留可逆方案和升级路径。若没有具体经历细节，使用真实协作原则并说不展开未发生情节。

### 4. 你做过最困难的技术决策是什么？

**参考落点**：可讲“LLM 不直接判断结构化事实 / 证据不足降级”或“中心不能主动访问内网时改为 Edge 主动同步”。给出替代方案、为何不选、风险和验证点。

### 5. 你认为自己当前最需要补齐什么？

**参考落点**：选择真实边界，例如生产级高并发容量规划、消息队列/K8s、完整监控平台或模型训练工程；说明已具备的基础、具体学习路径和不夸大已有经验。

### 6. 如果面试官质疑“这是不是只是调 API”，你如何回应？

**参考落点**：承认模型/外部服务是系统的一部分，重点说明你负责的业务建模、工具边界、RAG 依据、证据校验、状态机、幂等、取消/恢复、安全控制和人工确认；用一个具体项目串起来。

### 7. 你在团队中最适合承担什么角色？

**参考落点**：倾向业务与工程之间的 AI 应用实现：把不确定需求拆为可验证流程、接口和状态；不把自己包装为已具备所有 Infra 或 SOTA 训练能力。

### 8. 未来 1–3 年的职业规划是什么？

**参考落点**：短期扎实完成 AI 应用全链路并补工程可靠性；中期能独立负责受控 Agent 或 AI 产品模块的设计、评测和迭代；与目标岗位和团队业务相连，避免空泛管理路线。

### 9. 你为什么适合成都的这个岗位？

**参考落点**：先根据实际 JD 选择 Agent、全栈或研究侧的项目；强调能够快速在现有工程中用 Python/FastAPI、前端协作和受控 Agent 方法交付。不要假设公司业务、城市补贴或岗位技术栈。

### 10. 你有什么想问我们的？

**参考反问（选 2–3 个）**：

- 数据来源、权限和敏感信息边界通常如何设计？

## 六、问题修复闭环

对每道 `回答模糊`、`不会` 或 `表述有风险` 的题，按下面步骤完成：

1. **定位**：回到对应 Day 的项目卡、问答或代码事实，写出缺的是概念、项目细节、结构还是边界。
2. **查证**：只查真实简历、代码、文档或可靠资料；无法核实则保留“不确认”。
3. **简答**：写出三到六句“结论 → 项目/机制 → 风险”的答案。
4. **关联**：至少写一个真实项目落点；没有落点就标为通用知识，不冒充实践。
5. **再口述**：隔 10 分钟后脱稿回答一次，重新评分；仍低于 8 分则列入 `02_最后风险清单.md`。

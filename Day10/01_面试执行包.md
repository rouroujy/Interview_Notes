## 一、面试前 10 分钟取材路径

1. 看 JD：标出岗位类型、核心技术、业务场景和明确要求。
2. 从第二节选四张项目卡中的 2–3 张，按 `02_岗位讲述顺序与反问.md` 排序。
3. 从第三节选五类题库中的对应入口，只复习 JD 命中的题。
4. 看第四节事实边界和 Day9 风险清单，删除可能夸大的表达。
5. 用 60 秒说开场、60 秒说主项目、30 秒准备两个反问。

## 二、四张核心项目速查卡

### 1. 质量管理体系 Agent

**一句定位**：面向企业质量管理场景的可查询、可追溯分析 Agent，把结构化业务指标、质量体系文档依据和 LLM 归纳放在受控边界内，并通过 Edge 同步接入内网 GitLab Commit。

| 项目讲述项 | 面试口径 |
| --- | --- |
| 背景与约束 | 需要接入禅道 BUG、GitLab Commit、飞书需求文档和质量体系文件；中心无法主动访问分公司内网 GitLab。 |
| 总体方案 | LangGraph 完成意图识别→受控工具调用→结果生成；指标引擎计算业务事实，RAG 检索 checklist，LLM 做归纳。 |
| 核心决策 | 不让 LLM 直接计算或臆测结构化指标；ToolRegistry 收敛参数校验、权限、审计和测试边界。 |
| Edge 可靠性 | Edge 内网侧主动同步；SQLite Outbox 持久化待发批次，游标做增量，中心批次幂等接收，多实例数据隔离，Docker 化交付。 |
| 本人职责 | 使用“我设计/实现的具体工作流、工具边界或同步机制”表述，以简历与实际记录核对，不把团队能力全部归为个人。 |
| 验证与边界 | 强调可查询、可追溯和无依据判断风险降低；不补充未确认的线上规模、网络/证书拓扑或恰好一次语义。 |

**60 秒口述**：

> 我做的质量管理体系 Agent 面向企业内部质量场景，核心不是让模型直接下结论，而是先把事实和依据分开：BUG 严重等级、功能分布、激活和需求变更等由指标引擎通过受控工具计算，质量体系 checklist 通过 RAG 提供依据，LLM 只在这些输入上做归纳和解释。针对中心不能主动访问分公司内网 GitLab 的约束，我参与实现了 Edge 主动同步：Edge 在内网读取数据，用 SQLite Outbox 记录待发送批次、游标做增量，中心按批次幂等接收。这样把跨网访问和重复投递风险收敛在可验证的流程中；具体生产网络和参数需要以部署记录核对。

**必答追问**：为什么不让 LLM 直连数据库？为什么 Edge 是主动同步？Outbox、游标和幂等各解决什么？

### 2. 成果评审 Agent

**一句定位**：面向 GitLab 仓库的证据驱动评审 Agent，按 checklist 生成可追溯的合规性评审草稿，并由人工确认归档。

| 项目讲述项 | 面试口径 |
| --- | --- |
| 背景与目标 | 让评审结果有明确来源，不是只生成一段看似合理的结论。 |
| 总体方案 | 9 节点 LangGraph 串联清单加载、仓库快照、目录/依赖解析、事实提取、证据组装和逐项裁决。 |
| 可信性决策 | 每项结论关联文件路径、行号、快照 SHA；校验 LLM 输出的证据索引；无证据/非法引用降级为“无法确认”。 |
| 长任务工程 | 创建、执行、待人工确认、取消、失败、重启中断等状态；幂等创建、进度跟踪、取消/重试和审计记录。 |
| 安全边界 | 只读 GitLab Token、源码不落库、并发与文件大小限制；人工确认后归档。 |
| 不能夸大 | 已确认后台线程和有界并发；不说已使用消息队列、分布式 worker、WebSocket、K8s 或完成高并发压测。 |

**60 秒口述**：

> 成果评审 Agent 的目标是把 GitLab 仓库按 checklist 生成可追溯的评审草稿。我设计并实现的关键点是把一次生成拆为 9 节点工作流：先固定仓库快照，再解析目录和依赖、提取事实、组装证据，最后逐项裁决。为了避免模型无依据判断，我为结论关联文件路径、行号和快照 SHA，并校验证据索引；没有证据或引用非法时统一降级为“无法确认”，由人工确认归档。工程上任务状态覆盖创建、执行、待确认、取消、失败和重启中断，配合幂等创建、进度和审计，确保长任务可追踪；当前实现边界是后台线程和有界并发，而不是完整分布式调度平台。

**必答追问**：为什么不能一次 Prompt？证据索引如何防幻觉？状态机如何处理取消和重启？

### 3. AI Coding Harness

**一句定位**：面向 Claude Code / Codex 的最小受控 AI 开发框架，让 AI 理解工程上下文、遵守架构约束，并保留人工审批责任。

| 项目讲述项 | 面试口径 |
| --- | --- |
| 问题 | AI 编程工具若只拿到即时需求，容易忽略架构约束、接口契约、稳定决策和测试要求。 |
| 上下文机制 | 将 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等沉淀为可复用工程上下文。 |
| 闭环 | 业务建模→任务单人工确认→AI 编码与测试→人审验收→归档续接。 |
| 核心决策 | Context Engineering 是把最小必要、可更新、可追溯的约束交给工具，不是无限堆 Prompt。 |
| 人工边界 | 关键业务责任不由 AI 自动越权；审查和验收是流程的一部分。 |
| 不能夸大 | 不说 AI 自动上线、替代人工开发，也不与成果评审 Agent 混为同一项目。 |

**60 秒口述**：

> 我搭建的最小 AI Coding Harness 是为企业 Agent MVP 服务的受控开发框架。它解决的问题是，AI 编程工具只看当前需求时很容易忽略已有架构和协作决策，所以我把架构约束、接口契约、测试策略、稳定决策和任务状态沉淀为 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等工程上下文。开发流程先做业务建模和任务单人工确认，再让 AI 编码与测试，最后经人审验收并归档续接。这样 AI 可以提升实现效率，但关键业务决策、变更范围和验收责任始终由人控制；它不是自动上线平台，也不是成果评审 Agent 的替代品。

**必答追问**：Context Engineering 和 Prompt 有何区别？如何避免上下文过期？AI 改错接口怎么办？

### 4. 论文引用查证 Agent

**一句定位**：面向论文 PDF 的 Agent + RAG 系统，完成解析、检索、引用合理性判断和结构化输出；证据不足时明确返回“无法确认”。

| 项目讲述项 | 面试口径 |
| --- | --- |
| 数据链路 | GROBID 解析 PDF 并提取 TEI XML，完成文本切分、向量化、FAISS 检索和元数据过滤。 |
| 检索决策 | Hybrid RAG：BM25 + FAISS + Rerank，兼顾关键词匹配、语义召回与排序质量。 |
| 评测 | 用人工标注集从 Recall@k、证据覆盖率、判定准确率检查检索与查证效果。 |
| 工程化 | 解析、检索、引用验证封装为受控工具；FastAPI 服务；Redis 缓存、Docker、日志和异常处理。 |
| 可靠性 | 证据不足时返回“无法确认”，而不是强行判定。 |
| 不能夸大 | 没有确认的具体评测分数、缓存 key/TTL、线上规模与部署细节不补造。 |

**60 秒口述**：

> 论文引用查证 Agent 的目标是判断论文中的引用是否有可检索证据支持。流程从 GROBID 解析 PDF、提取 TEI XML 开始，再做文本切分、向量化和元数据过滤；检索采用 BM25、FAISS 和 Rerank 组成的 Hybrid RAG，以同时覆盖术语匹配、语义召回和排序质量。评测使用人工标注集，看 Recall@k、证据覆盖率和判定准确率。工程上把解析、检索和验证封装为受控工具，用 FastAPI 服务，并结合 Redis、Docker、日志和异常处理交付。这个项目最重要的边界是证据不足就返回“无法确认”，具体分数和缓存配置要以实验与代码记录为准。

**必答追问**：为什么 Hybrid RAG？Recall@k、证据覆盖率、判定准确率分别检查什么？PDF 解析失败如何处理？

## 四、统一事实边界卡

| 主题 | 可以稳定说 | 不能说 |
| --- | --- | --- |
| LLM 作用 | 归纳、解释、受控工具编排、基于证据裁决 | LLM 自己计算确定性业务指标或无证据定论 |
| 数据可靠性 | Outbox、游标增量、批次幂等实现至少一次投递下的业务去重 | 恰好一次投递 |
| 长任务 | 后台线程、有界并发、状态机、协作式取消、重启中断标记 | 已用分布式 worker 或毫秒级强杀取消 |
| 前端实时性 | 轻舟周期刷新、事件去重、暂停/恢复；可解释 WebSocket 方案 | 轻舟已使用 WebSocket |
| 工程基础设施 | Docker、日志、异常处理、Redis 缓存（论文项目） | K8s、高并发压测、全链路监控平台已上线 |
| 模型研究 | 红外课题的已确认协议、模型、设计和指标 | LLM 微调、RL、训练框架是既有项目经验 |
| 项目归属 | 按“我负责 / 我参与 / 团队完成”说明 | 所有系统均独立完成 |

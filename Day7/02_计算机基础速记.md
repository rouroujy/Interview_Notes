# 计算机基础速记：网络、操作系统与 Agent 场景

> **使用方式**：每个问题先给定义，再讲工程影响，最后关联真实项目或明确说明只是通用方案。

---

## 一、网络高频问题

### 1. HTTP 常用方法与幂等性

| 方法 | 语义 | 幂等性提示 |
| --- | --- | --- |
| GET | 读取资源 | 应无副作用，通常幂等 |
| POST | 创建或触发动作 | 通常非幂等，需要幂等键等保护 |
| PUT | 整体替换指定资源 | 语义上通常幂等 |
| PATCH | 部分更新 | 是否幂等取决于具体操作 |
| DELETE | 删除资源 | 语义上应尽量幂等，重复删除需定义返回行为 |

**项目映射**：评审任务创建是 POST，但使用 `idempotency_key` 防止重复执行；取消、重试等动作需通过状态机限制合法迁移。

### 2. 常见 HTTP 状态码

| 状态码 | 含义 | 面试场景 |
| --- | --- | --- |
| 200 / 201 / 202 | 成功 / 已创建 / 已接受异步处理 | 长任务创建可返回 202 或按接口约定返回创建结果 |
| 400 / 422 | 请求格式或语义校验失败 | Pydantic/业务参数校验 |
| 401 / 403 | 未认证 / 无权限 | API、GitLab Token、敏感数据访问 |
| 404 | 资源不存在 | `task_id` 或项目不存在 |
| 409 | 冲突 | 幂等键/状态迁移冲突可按约定使用 |
| 429 | 限流 | 高负载或外部 API 配额保护 |
| 500 / 502 / 503 / 504 | 服务内部/网关/不可用/超时 | 外部 GitLab、LLM、依赖异常 |

### 3. HTTP 与 HTTPS/TLS 的区别

> HTTP 是应用层请求响应协议；HTTPS 是 HTTP 运行在 TLS 之上，提供服务器身份认证、传输机密性和完整性保护。TLS 握手会协商协议和密钥、验证证书，后续用会话密钥加密传输。HTTPS 不能替代应用层鉴权、参数校验或最小权限。

**项目映射**：Edge 主动同步需要在不扩大跨网边界的前提下保护传输和身份；具体证书和网络配置需以实际部署核实。

### 4. TCP 三次握手与四次挥手

**三次握手**：客户端 `SYN` → 服务端 `SYN+ACK` → 客户端 `ACK`，双方确认收发能力并同步初始序号。

**四次挥手**：一方 `FIN` → 对方 `ACK` → 对方处理完剩余数据后 `FIN` → 原方 `ACK`。因为连接是全双工，双方关闭发送方向可能分开。

**工程影响**：网络调用可能连接失败、读写超时、半关闭或重试；因此 Edge/LLM/GitLab 调用需要 timeout、重试和幂等，而不能假设请求“没报错就一定完成”。

### 5. Cookie、Session、JWT 如何选择

| 方式 | 特点 | 风险/边界 |
| --- | --- | --- |
| Cookie | 浏览器自动携带的小型状态载体 | 需关注 Secure、HttpOnly、SameSite、CSRF |
| Session | 服务端保存会话，客户端持 Session ID | 多实例下需共享存储或粘性策略 |
| JWT | 客户端携带签名 token，服务端可无状态验证 | 吊销、过期、泄露与权限变更仍需设计 |

> 不存在绝对更好的方案，要按浏览器场景、跨域、会话撤销、多实例和安全要求选择。当前材料不把某种具体登录方式说成已实现。

### 6. 什么是 CORS

> CORS 是浏览器的同源策略下，服务端通过响应头允许特定来源、方法和 header 跨域访问的机制。它主要约束浏览器，不是后端鉴权；即使 CORS 放开，服务端仍需认证、授权和输入校验。

### 7. 轮询与 WebSocket 如何选择

> 轮询简单、易部署，适合状态变化较低频且允许短延迟的任务查询；WebSocket 适合需要实时多事件推送的交互，但要管理长连接、鉴权、断线重连和资源。评审 Agent 已确认有任务状态/进度查询；是否使用 WebSocket 未确认，只能讲取舍。

### 8. HTTP 超时与重试为何危险

> 客户端超时并不代表服务端未执行，盲目重试可能创建重复任务或重复写入。因此重试需要幂等键、请求去重、退避、超时边界和可观测错误码。Edge 同步的中心端幂等接收就是处理这一类不确定结果。

## 二、操作系统与并发高频问题

### 1. 进程、线程、协程区别

| 概念 | 资源与调度 | 适合 |
| --- | --- | --- |
| 进程 | 独立地址空间，隔离更强，切换成本更高 | CPU 密集、隔离需求强的任务 |
| 线程 | 同进程共享内存，切换较轻但同步复杂 | 阻塞 I/O 包装、短后台工作 |
| 协程 | 用户态协作调度，通常单线程内切换 | 大量 I/O 等待任务 |

**项目映射**：评审任务存在后台线程与受控外部 I/O；这不等于已实现多进程分布式执行。

### 2. I/O 密集与 CPU 密集如何选择并发方式

> I/O 密集任务大量时间等待网络、数据库或文件，协程/异步 I/O 或线程能提高并发；CPU 密集任务受 GIL 或 CPU 核数限制，更适合进程池、外部计算服务或任务队列。先判断瓶颈，再选并发模型。

**项目映射**：GitLab/LLM 请求更偏 I/O 等待，评审服务因此关注并发上限、timeout 和取消；大规模解析/模型计算的实际执行方式需要核实。

### 3. 死锁的四个必要条件

1. 互斥：资源一次只能被一个执行单元占用。
2. 占有并等待：持有资源同时等待其他资源。
3. 不可剥夺：资源不能被强制释放。
4. 循环等待：存在资源等待环。

**避免思路**：固定锁顺序、缩短持锁时间、避免在持锁时外部调用、超时/try-lock、减少共享可变状态。

### 4. 为什么不能在持有数据库事务时做长外部调用

> 会延长锁和连接占用，降低吞吐并增加死锁/超时风险。任务系统常先短事务持久化状态后提交，再调用 GitLab/LLM；结果回来再用短事务更新状态并校验版本。

### 5. 什么是上下文切换，为什么关注它

> 上下文切换是 CPU 从一个线程/进程切换到另一个执行单元时保存和恢复状态的开销。线程/协程数量无限增长会带来调度、内存和竞争开销，因此项目中使用有界并发而不是无限启动任务。

### 6. 内存泄漏和资源泄漏的常见来源

- 未关闭 HTTP 连接、文件句柄、数据库会话。
- 缓存无上限或任务结果长期不清理。
- 后台线程/协程未结束，队列不断积压。
- 大文件/源码正文常驻内存或日志。

**项目映射**：评审模块明确源码不落库，任务有资源限制和阶段 timeout；具体内存监控数据未确认。

### 7. 取消为什么要协作式处理

> 强杀线程可能破坏锁、事务和文件写入。协作式取消在安全点检查 `cancel_requested`，使当前批次/节点有机会释放资源和写入稳定终态；代价是取消有响应延迟。

## 三、项目化追问

### Agent 长任务为什么可能使用轮询而非 WebSocket？

> 如果任务状态变化频率不高、前端只需要阶段和进度，轮询实现简单且连接治理成本低。若需要实时多事件推送、多人协作状态或更低延迟，再评估 WebSocket。无论选择哪种，后端都要先有持久化任务状态、心跳、错误码和取消逻辑；推送通道不能替代任务系统。

### Edge 同步中网络失败如何处理？

> 网络失败时不能判断中心是否已处理该批次：Edge 保留 Outbox 记录并重试，游标避免重复全量读取，中心按幂等键去重。这样实现至少一次投递加幂等处理，不把网络不确定性隐藏掉。

### 如何把算法能力关联到工程能力？

> 我不会硬说业务代码就是 LeetCode。算法训练帮助我在工程中先识别问题结构，例如用哈希去重、用队列做状态推进、用二分/游标缩小搜索范围、用复杂度意识避免全量扫描；但是否采用某算法仍以业务数据量、可维护性和真实性能验证为准。

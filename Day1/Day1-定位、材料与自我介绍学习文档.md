# Day 1：定位、材料与自我介绍学习文档

> **适用岗位**：AI 应用工程师、Agent 工程师、AI 全栈工程师。  
> **使用方式**：按本文顺序完成内容、口述练习和材料填写；当天结束时，直接使用 `自我介绍.md`、`行为面试题库.md`、`岗位JD关键词表.md` 进行学习和练习。  
> **Day 1 的目标**：让面试官在最初几分钟内理解你的方向、亮点和岗位匹配度，并让之后的项目追问自然落在你最有优势的 Agent/RAG 工程实践上。

## 二、个人定位：先统一面试主线

## 1. 推荐定位

### 一句话定位

> 我是一名具备前后端工程经验的人工智能硕士，重点方向是将 LLM、RAG 和工作流编排落地为**可追溯、可控、可交付**的企业 Agent 系统。

### 面试中的个人标签

> **证据驱动、可靠性约束、工程化交付。**

这三个词不是口号，必须有对应项目证据：

| 标签 | 简历中的支撑证据 | 面试中可使用的表达 |
| --- | --- | --- |
| 证据驱动 | 成果评审 Agent 关联文件路径、行号和快照 SHA；论文查证系统证据不足时返回“无法确认” | “我不会让模型直接给结论，而是要求结论能回溯到代码、文档或检索证据。” |

## 2. 三类岗位的表达侧重点

| 岗位方向 | 面试主讲项目顺序 | 应重点强调 | 降低篇幅的内容 |
| --- | --- | --- | --- |
| Agent 工程师 | AI Coding Harness → 成果评审 Agent → 质量管理体系 Agent | 上下文工程、任务拆解、人工审批、LangGraph、工具调用、状态机、证据链 | 过多展开传统前端细节 |

## 3. 面试中暂不使用的定位

- 不将自己定位为“纯算法工程师”或“大模型训练工程师”：当前核心竞争力是 AI 应用和 Agent 工程落地。
- 不只说“我会 LangChain/LangGraph”：工具名不是竞争力，系统边界、可靠性设计和业务交付才是。
- 不将自己介绍成“什么都会的全栈”：保留全栈能力作为工程优势，但始终围绕 AI 应用主线。

## 1. 1 分钟版

### 适用场景

- 面试开场“请做一下自我介绍”。
- HR 初筛、电话面、宣讲会沟通。

### 推荐稿

> 面试官您好，我叫焦月，目前是中国科学院大学人工智能专业硕士，预计 2027 年毕业。本科是物联网工程，此前有全栈开发经历，目前在赛目科技做 AI 应用开发实习。我的求职方向是 AI 应用和 Agent 工程。  
> 我最近的工作主要围绕企业 Agent 的可靠性落地：一方面，我用 LangGraph、受控工具调用和 RAG 构建质量管理分析流程，将结构化指标计算和规范性检索依据分开；另一方面，我参与代码成果评审 Agent 的设计，让每项结论关联代码文件、行号和快照 SHA，并在证据不足时降级为无法确认。  
> 我的优势是既能完成 FastAPI、数据库和任务状态机等工程实现，也会从证据、权限、异常恢复和人工确认角度约束模型输出。我希望在贵司参与将 LLM/Agent 能力真正交付到业务场景的工作。

### 必须替换项

- 将“贵司”替换为公司名或业务方向；不要在最终面试中机械保留“贵司”。
- 如岗位偏 RAG，可将“代码成果评审 Agent”替换为“论文引用查证系统的 Hybrid RAG 与评估”。
- 如岗位偏 AI Coding、研发效能或开发者工具，可将第二个项目替换为“面向 Claude Code/Codex 的最小 AI Coding Harness”，强调上下文工程、任务单和人工审批闭环。
- 如岗位偏全栈，可增加一句“我也有 Vue、后端接口和第三方服务集成经验”。

### 口述检查

- [ ] 开头 15 秒内说出：身份、学历、毕业时间、求职方向。
- [ ] 至少举出 2 个与目标岗位相关的项目证据。
- [ ] 明确说出个人标签中的至少两个：证据驱动、可靠性约束、工程化交付。

## 2. 3 分钟版

### 适用场景

- 技术一面、业务一面开场。
- 面试官需要更完整的教育/经历脉络。

### 推荐结构

1. 教育与转向 AI 应用的路径。
2. 当前实习中的两个核心 Agent 项目。
3. 论文引用查证系统或工程基础作为补充。
4. 自己的差异化能力和求职诉求。

### 推荐稿

> 面试官您好，我叫焦月，目前是中国科学院大学人工智能专业硕士，预计 2027 年毕业。本科是物联网工程，早期有 Vue、PHP/MySQL 等全栈研发经历，也参与过基于 OpenAI API 的内容生成产品。因此我逐步从传统业务系统研发转向了 LLM 应用和 Agent 工程方向。  
> 目前我在赛目科技担任 AI 应用开发实习生，主要参与企业内部质量场景的 Agent 开发。第一个项目是质量管理体系 Agent，它接入禅道 BUG、GitLab Commit、飞书需求文档和质量体系文件。我重点参与了工作流和工具边界的设计：对于缺陷等级、功能分布等结构化事实，通过受控工具和指标引擎查询；对于质量规范和 checklist，通过 RAG 提供原始依据；LLM 只在这些事实和依据之上做归纳。这样可以避免模型在质量分析中无依据地推断。  
> 第二个项目是功能开发成果评审 Agent，面向 GitLab 仓库按 checklist 生成合规性评审草稿。我参与设计了串联清单加载、仓库快照、事实提取、证据组装和逐项裁决的 LangGraph 流程。这个项目最关注的是可追溯性：每项结论都要关联文件路径、行号和快照 SHA；如果模型引用不存在或证据不足，系统不会强行给出结论，而是降级为“无法确认”。同时我们还围绕幂等创建、进度跟踪、取消/重试和服务重启中断处理设计了任务状态机。  
> 此外，我还自建了一个面向 Claude Code/Codex 的最小 AI Coding Harness，用于企业 Agent MVP 的受控开发。它把架构约束、接口契约、测试计划、任务状态和稳定决策沉淀为可复用上下文，并形成“业务建模、任务单人工确认、AI 编码与测试、人审验收、归档续接”的闭环。这个项目让我进一步理解：Coding Agent 的关键不只是代码生成，而是如何让它在正确的上下文和审批边界内工作。  
> 除了实习项目，我还做过论文引用查证智能体，完成了 GROBID 解析、BM25 + FAISS + Rerank 的混合检索链路，并通过人工标注集评估召回、证据覆盖和判定结果。这些经历让我形成了一个比较明确的做事方式：不仅关注模型能否生成答案，更关注答案是否有证据、系统是否可控、失败时能否安全降级。  
> 我希望应聘 AI 应用或 Agent 工程师岗位，结合我的 Python/FastAPI、数据库、前端和 Agent 工程经验，参与把模型能力落地为稳定的业务系统。

### 口述检查

- [ ] 叙述顺序是“经历演进 → 当前核心工作 → 技术差异化 → 求职匹配”。
- [ ] 两个核心 Agent 项目各有一个清晰的技术亮点；如果岗位偏 Coding Agent，再加入 Harness 的上下文工程与人工审批亮点。
- [ ] 可根据 JD 在 30 秒内切换为 Agent、RAG 或全栈侧重点。
- [ ] 面试官打断时，能停在一个完整句子处并按问题展开。

## 3. 5 分钟项目导向版

### 适用场景

- 面试官要求“详细介绍最近做的项目”。
- Agent、后端工程化、企业应用方向的技术面。

### 默认主讲项目：质量管理体系 Agent

> 我想重点介绍一下我在实习中参与的质量管理体系 Agent。它面向企业内部质量管理场景，接入禅道的 BUG 数据、GitLab Commit、飞书需求文档和质量体系文件，目标是帮助研发和质量团队查询质量指标、分析缺陷问题，并给出有依据的质量分析结果。  
> 这个项目一开始最重要的判断是，不能把所有材料直接交给大模型后让它自由回答。因为 BUG 严重等级、模块分布、激活情况等属于结构化业务事实，如果依赖模型从大量文本中归纳，容易产生统计错误；而质量体系 checklist、流程规范等属于文档知识，需要给出原始依据。因此我们把系统拆成三部分：结构化数据经过指标引擎和受控工具计算；质量体系文件通过 RAG 检索并返回相关依据；LLM 负责识别用户意图、编排工具调用，并在事实和依据的范围内生成结果。  
> 在工作流上，我们使用 LangGraph 组织“意图识别 → 受控工具调用 → 结果生成”的流程。我的工作重点之一是工具注册与调用边界：将缺陷等级、功能分布、激活、需求变更等指标封装为独立工具，使每个工具都有明确的输入参数、返回结构与调用范围。这样一方面方便后续扩展新的指标，另一方面也避免模型直接拼接不受控的查询或跨权限访问数据。  
> 另一个难点是需求变更的判定。缺陷历史记录中存在大量非结构化描述，单纯依赖规则覆盖有限。我们使用 LLM 对历史记录进行需求变更标注，并将结果落库复用；但这个标注不直接等同于最终事实，而是作为后续分析可复查的数据。对于真正需要确认的业务结论，仍要回到原始记录、指标结果和质量体系依据。  
> 这个项目的核心价值在于建立责任边界：结构化指标由确定性计算负责，规范解释由 RAG 提供证据，LLM 负责受约束的归纳。当数据不完整或检索不到依据时，系统应明确说明限制，而不是生成看似合理但没有支撑的结论。  
> 如果继续迭代，我会优先完善三点：第一，构建典型质量问题的离线评估集，评估工具选择和回答依据的准确性；第二，为关键结论增加更细粒度的数据来源和时间范围展示；第三，补充工具调用、检索命中与回答结果的链路追踪，便于线上排障和持续优化。

### 备选主讲项目：功能开发成果评审 Agent

如果 JD 更强调代码智能、研发效能、软件工程 Agent，使用以下主线替换上面的项目部分：

> 这个项目面向 GitLab 代码仓库，目标是根据既定 checklist 自动生成可追溯的合规性评审草稿，并由人工确认归档。项目的关键不是让模型“看起来像在审代码”，而是确保每项结论都有具体证据。  
> 因此我们设计了从清单加载、仓库快照、目录与依赖关系解析、事实提取、证据组装到逐项裁决的 9 节点 LangGraph 工作流。评审结论不只是一句自然语言，而要关联文件路径、行号和仓库快照 SHA。对于 LLM 返回的证据引用，系统会做索引校验；引用不存在、越过快照边界或不足以支撑结论时，统一降级为“无法确认”。  
> 工程上，我们还设计了覆盖创建、执行、待人工确认、取消、失败和服务重启中断处理的任务状态机，并支持幂等创建、进度跟踪、取消/重试和审计记录。源码使用只读 GitLab Token 获取且不落库，同时限制文件大小与并发，控制安全和资源风险。  
> 这个项目让我最深的体会是，企业 Agent 的难点往往不是“让模型能调用工具”，而是如何管理任务生命周期、约束模型证据、保留人工责任边界，并在失败时以安全方式降级。

### 备选主讲项目：最小 AI Coding Harness

> 这个项目的背景是，企业希望使用 Claude Code 或 Codex 这样的 AI 编程工具快速完成 MVP 开发，但直接让 Agent 在仓库中自由修改代码会带来几个问题：它不了解项目的稳定架构决策和接口约束，任务边界容易漂移，生成代码也可能绕过测试和人工审批。  
> 因此我自建了一个最小 AI Coding Harness，目标不是替代工程师，而是为 AI 编程工具提供受控的协作框架。我把架构约束、接口契约、测试策略、已确认的稳定决策和任务状态沉淀为结构化工程上下文，形成 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等协作材料。这样 Agent 在开始编码前可以先理解任务范围、不能违反的契约和验收方式，而不是只根据一句自然语言需求猜测实现。  
> 在流程上，我设计了“业务建模 → 任务单人工确认 → AI 编码与测试 → 人审验收 → 归档续接”的闭环。人工确认不是为了降低自动化程度，而是把业务目标、改动范围和关键责任在编码前锁定；AI 负责在明确任务单下生成和验证代码；人审决定是否接受变更；归档后的任务、决策和契约又成为下一轮工作的可靠上下文。  
> 这个项目让我关注到 Coding Agent 的核心挑战是上下文工程和治理，而不是单次代码生成效果。后续如果继续迭代，我会增加任务与代码变更的可追溯关联、自动化测试结果采集、权限分级以及针对不同仓库的上下文初始化机制，并通过任务完成率、返工率、测试通过率和人工修改率评估它的效果。

### 5 分钟版检查

- [ ] 讲清业务问题、约束、架构、本人职责、技术决策、难点、结果/价值、后续改进。
- [ ] 至少讲清一个“为什么不用更简单方案”的决策。

## 五、行为面试题库：STAR 答案

> **STAR 原则**：`S` 情境（Situation）→ `T` 任务（Task）→ `A` 行动（Action）→ `R` 结果（Result）。  
> 回答时，`A` 至少占一半；优先说“我做了什么、为什么这样做”，避免全程使用“我们”。

## 1. 为什么转向 AI 应用 / Agent 方向？

### 回答参考

- **S**：我本科和早期工作主要是物联网、前端和全栈开发，2023 年曾参与基于 OpenAI API 的内容生成与发布流程。
- **T**：我希望找到既能发挥已有工程能力、又能解决更复杂信息处理问题的技术方向。
- **A**：在接触 LLM 应用后，我发现模型能力只有与数据、工具、工作流、权限和业务流程结合，才能形成真正可用的产品。因此研究生阶段选择人工智能方向，并持续投入 RAG、LangGraph、工具调用和工程化实践。
- **R**：目前我在企业质量管理和代码评审场景中做 Agent 开发，也完成论文引用查证 RAG 系统。我确认自己更适合做模型能力落地、可靠性设计和工程交付交叉处的工作。

- **T**：我需要参与设计一个既能自动化执行、又能保留人工确认和审计边界的评审流程。
- **A**：我参与拆分并实现 LangGraph 工作流中的仓库快照、事实提取、证据组装和逐项裁决等环节；为结论关联路径、行号和 SHA，并设计证据索引校验。对于任务执行侧，我参与梳理幂等创建、取消、重试与服务重启中断等状态迁移，避免长任务出现状态不一致。

## 6. 遇到需求变化时，你如何处理？

### 回答参考

- **S**：企业质量管理的分析诉求会随项目阶段变化，例如新增指标、新的数据源或对结论依据提出更细要求。
- **T**：需要在不破坏既有流程的情况下，快速支持变化并保证历史任务可追溯。
- **A**：我会先澄清变化影响的是数据口径、业务规则、工具能力还是展示方式；然后将新增能力封装为独立工具或配置项，明确输入输出和权限边界。涉及结论口径时，会保留版本和数据来源，避免同一问题在不同时间得到无法解释的结果。
- **R**：这种拆分使系统扩展尽量局限在对应工具、指标或 checklist 层，而不是修改整个 Agent 主流程。

## 7. 你如何处理技术分歧？

### 回答参考

- **S**：在 Agent 项目中，常见分歧是“是否让模型直接判断”与“是否增加确定性校验/人工确认”之间的效率和可靠性权衡。
- **T**：需要在交付速度、用户体验和业务风险之间达成可执行方案。
- **A**：我会先把争论转化为可验证的问题：结论的风险等级是什么、是否需要追溯依据、错误的代价是什么、能否通过小样本或评估集比较方案。对于高风险结论，我倾向于保留证据校验和人工确认；对于低风险摘要类能力，可以适度放宽自动化边界。
- **R**：团队讨论会从“谁的直觉更对”转为“在什么约束下选择什么方案”，最终方案也更容易被复用和解释。

## 8. 项目延期或任务推进受阻时，你如何处理？

### 回答参考

- **S**：Agent 项目通常涉及外部数据源、代码仓库权限、文档质量和模型输出稳定性，任何一项都可能拖慢整体进度。
- **T**：在保证核心价值的前提下控制风险，并让协作方及时知道阻塞点。
- **A**：我会把任务拆成可独立验证的最小链路，优先保障“数据获取 → 工具/检索 → 有证据的结果输出”主流程；对于不稳定能力设置 mock、降级或人工确认。出现阻塞时明确记录依赖方、影响范围、替代方案和需要决策的事项，而不是等到截止时间才反馈。
- **R**：即使部分增强能力延后，也能先交付可验证的 MVP，并为后续迭代保留清晰的边界。

## 9. 讲一次你如何处理异常或失败结果？

### 回答参考

- **S**：在论文引用查证场景中，PDF 解析可能失败，或检索结果无法覆盖引用判定所需的上下文。
- **T**：不能因为系统无法确认就生成貌似合理的判断。
- **A**：我将解析、检索和判定拆开处理：解析失败时返回明确的失败原因；检索证据不足时将结果标记为“无法确认”，并保留已检索到的证据和限制说明；接口侧结合日志和异常处理，便于定位具体失败阶段。
- **R**：系统虽然会在部分样本上拒答，但避免了无证据结论，符合引用查证场景对可靠性的要求。

### 达标标准

在不看稿的前提下，能够流畅回答下面这段开场问题：

> “请你做一下自我介绍，并重点说说你最近的 Agent 项目。”

回答必须让面试官明确知道：

1. 你要找的是 AI 应用 / Agent 工程岗位。
2. 你有真实的企业 Agent、RAG 和全栈工程实践。
3. 你的核心特点是**用证据、边界和工程机制提高 Agent 系统的可靠性**。
4. 继续追问时，应优先进入质量管理 Agent 或成果评审 Agent，而不是泛泛讨论技术栈。

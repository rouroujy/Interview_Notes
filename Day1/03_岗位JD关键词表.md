## 二、可直接背诵的关键词答案

### LangGraph

> LangGraph 是我用来组织有状态 Agent 工作流的框架。在质量管理 Agent 中，我用它串联“意图识别、受控工具调用、结果生成”；在成果评审 Agent 中，则实现了 9 节点流程。相比在代码里临时串联模型调用，它更容易把节点、状态和人工确认边界表达清楚。它的风险是流程变复杂后状态难维护，所以只应在确实存在多步骤和分支的场景使用，而不是为简单问答过度设计。

### Tool Calling 与 ToolRegistry

> Tool Calling 的作用是把模型从“自由猜测数据”变成“调用受控能力”。我在质量管理 Agent 中设计 ToolRegistry，把 BUG 严重等级、功能分布、激活和需求变更等指标封装为工具；结构化事实通过指标引擎计算，模型只基于工具结果做归纳。直接让模型阅读大量文本的替代方案实现快，但容易出现统计错误或无依据判断；因此工具的输入、返回和权限边界需要在后续项目中继续严格核验。

### RAG

> RAG 是在生成前检索相关原始资料，再让模型基于资料回答的模式。我在质量管理 Agent 中用它提供质量体系 checklist 的依据，在论文引用查证智能体中用它完成论文证据检索。它适合解决“结论需要文档依据”的问题，但不能替代结构化指标计算；如果检索不到足够证据，系统应说明限制或返回“无法确认”，而不是补全一个看似合理的答案。

### Hybrid RAG

> Hybrid RAG 是把关键词检索和向量检索结合，再通过重排序提高候选证据质量。我在论文引用查证智能体中使用 BM25、FAISS 和 Rerank：BM25 保留术语和精确关键词匹配，FAISS 处理语义相近表达，Rerank 再从候选中挑选与当前引用判断更相关的片段。它比只用一种检索方式更能覆盖不同 query，但会增加链路成本，因此需要用人工标注集和 Recall@k、证据覆盖率、判定准确率一起评估。

### Rerank

> Rerank 的位置在初步召回之后，用更精细的相关性判断重新排序候选证据。在论文引用查证场景中，我先用 BM25 和 FAISS 扩大候选范围，再重排后交给后续引用验证。只增加 top-k 不能保证候选真正相关，反而可能引入更多噪声；Rerank 的代价是额外时延和计算成本，所以应该只处理规模受控的候选集。

### Evidence-Grounded

> Evidence-Grounded 指的是结论必须被具体证据支撑，而不是只给模型一句判断。在成果评审 Agent 中，每项结论关联文件路径、行号和仓库快照 SHA，并对 LLM 返回的引用做证据索引校验。文件不存在、行号不合法或证据不足时，系统降级为“无法确认”。这比直接让模型审代码更可追溯，但它仍需要人工确认，不能把证据存在等同于结论一定正确。

### Human-in-the-loop

> Human-in-the-loop 是把人工确认保留在高风险决策节点，而不是让 Agent 完全自动执行。成果评审 Agent 生成的是评审草稿，由人工确认归档；AI Coding Harness 中，任务单先由人工确认，编码和测试后仍由人审验收。这样做会增加人工成本，但能把业务目标、改动范围和最终责任固定在可追溯的节点上。

### AI Coding Harness

> AI Coding Harness 是我为企业 Agent MVP 自建的受控 AI 开发框架。它把架构约束、接口契约、测试策略、稳定决策和任务状态沉淀为 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等上下文，并组织“业务建模、任务单人工确认、AI 编码与测试、人审验收、归档续接”的闭环。它的价值不在于替代工程师，而在于降低上下文漂移和越权改动风险。

### FastAPI

> FastAPI 是我在实习项目和论文引用查证智能体中用于服务化能力的框架。它适合把论文解析、上下文检索、引用验证等能力封装成接口，并与 Pydantic 等组件配合处理结构化输入输出。选择它不意味着接口天然高性能；长耗时的解析、检索和 Agent 任务仍要考虑异步边界、任务状态和异常处理，而不能只把所有逻辑堆在一个请求里。

### Redis

> Redis 在我的论文引用查证智能体中用于缓存。它适合缓存可重复使用的中间结果，减少不必要的解析或检索开销，但不能替代数据库中的事实来源。使用缓存时需要明确缓存键、失效策略和数据不一致风险；简历没有给出缓存命中率或性能指标，因此面试中只说明它承担的缓存角色。

### MySQL、SQLAlchemy 与 Alembic

> MySQL、SQLAlchemy 和 Alembic 是我实习项目技术栈中的后端基础，也与我早期 PHP/MySQL 全栈经验衔接。MySQL 存放需要持久化管理的业务数据，SQLAlchemy 用于对象与数据表之间的访问，Alembic 管理数据库结构演进。ORM 能提高开发效率，但不能替代对索引、事务和查询成本的理解；这些细节会在后端专题中继续展开，而不把它们虚构成当前项目的线上优化指标。

### Docker

> Docker 用于把运行环境和应用交付方式固定下来。我在论文引用查证智能体中结合 Docker 完成工程化交付，在分公司数据接入中也结合 Docker 化交付 Edge 同步能力。它减少环境差异，但不自动解决配置、日志、数据卷和资源限制问题；因此我会把 Docker 作为可复现交付的一部分，而不是把“容器化”直接等同于生产稳定性。

### Edge 主动同步

> 在质量管理 Agent 中，中心系统无法主动访问分公司内网的 GitLab，因此我实现由 Edge 端主动发起的同步架构，将分公司的 Commit 安全接入中心质量看板。它的关键取舍是遵守网络边界：不要求中心跨网拉取，而由受限网络一侧把数据同步出来。这个方案解决的是数据接入与隔离问题，不应夸大为已证明的实时性或高吞吐能力。

### SQLite Outbox

> SQLite Outbox 在 Edge 同步中用于保存待同步数据，使待发送的数据有明确的本地落点。它解决的是同步动作和待同步数据脱节的风险；单独使用 Outbox 不能自动避免重复接收，所以还需要游标增量和中心端的批次幂等接收配合。我的简历记录了该机制，但没有给出失败率或数据量指标，面试中应如实说明这一边界。

### 游标增量同步与批次幂等接收

> 游标增量同步用于定位已经处理到的位置，让 Edge 后续聚焦新增 Commit；中心按批次幂等接收，则避免重试或重复发送造成重复处理。两者分别解决“同步范围定位”和“重复接收控制”，不能相互替代。同步中断时，应以已保存的待同步数据和游标为基础继续处理；具体重试间隔、告警阈值和补偿策略不在简历中，我不会把它们说成既有实现。

## 三、公司与岗位匹配的直接回答

### 为什么选择 AI 应用 / Agent 工程岗位？

> 我选择这个方向，是因为它正好连接了我的工程基础和人工智能学习经历。我早期做过前端、PHP/MySQL 全栈和基于 OpenAI API 的内容生成流程；研究生阶段进一步做了 RAG、Agent 和红外动作识别。目前在企业质量管理和代码评审场景中，我最有成就感的是把模型、数据、工具和业务流程组织成可追溯、可控的系统，所以我希望继续在 AI 应用或 Agent 工程岗位把这种能力做深。

### 为什么你适合这个方向？

> 我的匹配点有三类：第一，我有企业 Agent 和 RAG 的真实项目证据，包括 LangGraph 工作流、受控工具、Hybrid RAG 和证据校验；第二，我能完成 FastAPI、数据库、缓存、Docker 和 Vue 等工程链路；第三，我在项目中优先考虑证据、权限、异常降级和人工确认。我的边界也很明确：我不把自己定位为基础模型训练工程师，而是更擅长把模型能力可靠地交付到业务场景。

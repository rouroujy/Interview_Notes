# 行为面试题库

> **背诵规则**：动机与匹配题先给结论再说明经历；行为题统一按 `S 情境 → T 任务 → A 行动 → R 结果/复盘` 口述。以下 10 个 STAR 场景为：第 5—9 题、第 13—17 题。所有结果均以简历中的交付、验证方式或风险控制表述，不虚构线上指标。

---

## 1. 为什么转向 AI 应用 / Agent 方向？

> 我早期做过物联网、前端、PHP/MySQL 全栈开发，也在 2023 年参与过基于 OpenAI API 的内容生成和多平台发布流程。接触 LLM 应用后，我发现模型只有和数据、工具、工作流、权限及业务流程结合，才能成为真正可用的产品。研究生阶段我选择人工智能方向，并持续做 RAG、LangGraph 和 Agent 工程实践。现在我在质量管理、代码评审和论文引用查证场景中积累了经验，所以希望继续做模型能力落地、可靠性设计和工程交付交叉处的工作。

**追问：为什么不主攻大模型训练？**
我有红外动作识别课题，也会持续补齐 Transformer 和评估基础；但我当前最完整的积累在 AI 应用工程。我更擅长将模型接入真实数据和业务流程，处理检索、工具调用、接口、状态机、权限和异常降级。这个边界我会明确说明，而不会把应用经验包装成大模型训练经验。

## 2. 为什么选择 AI 应用 / Agent 工程岗位？

> 我选择这类岗位，是因为它既需要理解模型能力，也需要把能力稳定地接到业务里。我的经历正好覆盖这个组合：质量管理 Agent 区分结构化指标、RAG 依据和 LLM 归纳；成果评审 Agent 让结论回溯到文件、行号和 SHA；论文引用查证智能体用 Hybrid RAG 和人工标注集做评估；我还有 FastAPI、数据库、Docker 和 Vue 的工程基础。我希望在真实业务中继续把“模型可用”推进到“结果可信、系统可交付”。

**追问：面对具体公司如何回答？**
我会先了解该公司的 AI 业务场景和岗位中重复出现的两个关键词，再从现有项目中选择最接近的证据：企业知识和质量场景讲质量管理 Agent，研发效能讲成果评审 Agent 与 AI Coding Harness，文档智能讲论文引用查证，AI 全栈讲 Edge 同步和 Vue 前端。我不会在不了解业务的情况下编造“我很认同贵司”的理由。

## 3. 你最大的技术优势是什么？

> 我的优势是从工程可靠性的角度落地 Agent。我不只关注模型回答是否流畅，而是先区分哪些信息必须由确定性系统提供、哪些需要检索依据、哪些可以交给 LLM 归纳。质量管理 Agent 中，结构化指标由工具和指标引擎计算，质量体系文件由 RAG 提供依据；成果评审 Agent 中，每项结论关联路径、行号和快照 SHA，并在证据不足时降级。再加上我的后端和前端经历，我会同时考虑任务状态、网络边界、权限、异常恢复和用户交互闭环。

**追问：如何证明这个优势？**
我不使用没有依据的准确率来证明它，而是说明可验证的设计结果：成果评审 Agent 的引用会经过索引校验；质量分析不把统计事实交给模型自由推断；分公司内网数据通过 Edge 主动同步接入中心，而不是要求中心跨网拉取。这些机制不能保证所有结果都正确，但能把错误暴露出来并保留人工确认边界。

## 4. 你的短板是什么？

> 我的短板是大规模模型训练和分布式训练经验有限。我的项目更集中在 RAG、Agent 和应用工程化，所以我不会把自己定位为训练侧专家。为补齐这个边界，我会系统复习 Transformer、推理参数、评估方法，并在项目中通过标注集、日志和失败案例理解模型行为。对于当前求职方向更需要的应用工程能力，我有明确的项目证据；训练侧则作为持续补齐方向。

## 5. 最有挑战的项目是什么？你承担什么职责？

- **S**：功能开发成果评审 Agent 需要根据 GitLab 仓库和 checklist 生成合规性评审草稿，但模型直接阅读代码容易编造依据，难以满足可追溯要求。
- **T**：我需要把自动化评审做成可审计、可人工确认的流程，而不是只生成一段评语。
- **A**：我设计并实现了 9 节点 LangGraph 工作流，串联清单加载、仓库快照、目录与依赖关系解析、事实提取、证据组装和逐项裁决；为每项结论关联文件路径、行号和快照 SHA，并对 LLM 输出做证据索引校验。无证据或引用非法时，结果统一降级为“无法确认”。我还围绕任务创建、执行、待人工确认、取消、失败和服务重启中断等状态设计任务状态机，支持幂等创建、进度跟踪、取消/重试和审计记录。
- **R**：系统输出的是带证据的评审草稿，最终由人工确认归档。这个项目让我形成了一个判断：企业 Agent 的难点不只是模型调用，而是证据、任务生命周期和人工责任边界。

**追问：证据为什么要关联固定 SHA？**
因为代码会变化。关联本次任务的仓库快照 SHA，才能让路径、行号和结论对应同一版本；如果改用默认分支的最新代码，后续很难复现当时的评审依据。

## 6. 遇到需求变化时，你如何处理？

- **S**：质量管理的分析诉求会随项目阶段变化，例如新增指标、数据源或对结论依据提出更细要求。
- **T**：我需要支持变化，同时避免破坏既有工作流和历史结论的可解释性。
- **A**：我先判断变化属于数据口径、业务规则、工具能力还是展示方式；随后把新增指标或能力收敛为独立工具或配置项，保持输入、输出和调用范围清晰。涉及结论口径时，我会保留数据来源和版本信息，避免同一问题在不同时间得到无法解释的结果。
- **R**：改动被局限在指标、工具或 checklist 层，而不必重写整个 Agent 主流程；也为后续追查结论来源保留了基础。

**追问：如果新需求还没有完整评估集怎么办？**
我会先把能力限制在低风险范围，保留人工确认和明确的降级路径，同时记录工具调用、检索结果、模型输出和人工修改。高风险结论没有基本证据校验和拒答机制时，不应完全自动化上线。

## 7. 你如何处理技术分歧？

- **S**：在 Agent 项目中，常见分歧是“让模型直接给判断更快”还是“增加确定性校验和人工确认更可靠”。
- **T**：需要在交付速度、用户体验和错误成本之间形成可执行的选择。
- **A**：我会先把分歧转化为可验证的问题：结论的风险等级是什么、是否需要证据、错误的代价是什么、能否用小样本或评估集比较。对质量分析、代码评审这类高风险结论，我主张保留结构化计算、证据校验和人工确认；对低风险摘要类能力，可以适度放宽自动化边界。
- **R**：讨论从“谁的直觉更对”转向“在什么约束下选择什么方案”，也使最终设计更容易复用和解释。

## 8. 项目延期或推进受阻时，你如何处理？

- **S**：Agent 项目依赖外部数据源、代码仓库权限、文档质量和模型输出稳定性，任一环节受阻都会影响交付。
- **T**：我需要在保证核心价值的前提下控制风险，并让协作方尽早了解阻塞点。
- **A**：我把工作拆成可独立验证的最小链路，优先保障“数据获取 → 工具或检索 → 有依据的结果输出”。对不稳定能力准备 mock、降级或人工确认；出现阻塞时记录依赖方、影响范围、替代方案和需要决策的事项，而不是等到截止时间才反馈。
- **R**：即使增强能力需要后移，也能先形成可验证的 MVP，并保留清晰的迭代边界。

## 9. 讲一次你如何处理异常或失败结果？

- **S**：论文引用查证场景中，PDF 解析可能失败，或者检索证据无法覆盖引用判断所需的上下文。
- **T**：系统不能因为无法确认就生成貌似合理的结论。
- **A**：我将论文解析、上下文检索和引用验证封装为受控工具，并在 FastAPI 服务中结合日志和异常处理定位失败阶段。解析失败时返回明确失败原因；检索证据不足时返回“无法确认”，同时保留已有证据和限制说明。
- **R**：系统可能在部分样本上拒答，但避免了无证据结论。这比强行给出判断更符合引用查证场景对可靠性的要求。

## 10. 未来 3 年的规划是什么？

> 短期内，我希望在 AI 应用或 Agent 工程岗位中独立承担从需求理解、数据和工具接入、工作流设计、评估到上线观测的完整链路。中期我希望在可靠 Agent、RAG 评估或企业知识、研发效能等真实业务方向形成深度。长期我希望成长为既理解模型能力边界、又能负责复杂 AI 产品工程交付的人，而不是只局限于某个框架或一次模型调用。

## 11. 你为什么适合这个岗位？

> 我匹配这个方向的原因有三点。第一，我有 Agent 和 RAG 的真实场景：质量管理、代码评审、论文引用查证和受控 AI 编码。第二，我能完成从 FastAPI、数据库、缓存和 Docker 到 Vue 交互的工程链路。第三，我的项目方法是把结构化事实、检索依据、模型归纳和人工确认分开处理，优先保证可追溯和可控。对 AI 应用或 Agent 工程岗位而言，这些能力能帮助我较快参与真实业务系统的交付。

## 12. 你从一段不足的经历中学到了什么？

> 我在做 LLM 应用时逐渐认识到，初版 Demo 很容易只关注“能不能生成一个看起来正确的答案”，却忽略答案来源、错误成本和可复现性。后来在质量分析和代码评审场景中，我把这个认识落实为具体设计：结构化计算、检索依据和 LLM 归纳分层；对高风险结论增加证据校验和人工确认；对证据不足的结果明确降级。这让我从只关注功能实现，转向关注系统是否值得被信任。

## 13. 讲一次你如何处理受限网络下的数据接入问题？

- **S**：质量管理 Agent 需要使用分公司 GitLab 的 Commit 数据，但中心系统无法主动访问分公司内网。
- **T**：我需要在不要求中心跨网拉取数据的前提下，把分公司的 Commit 安全接入中心质量看板，并处理重复接收和多实例间的数据边界。
- **A**：我实现 Edge 端主动同步架构：用 SQLite Outbox 保存待同步数据，用游标进行增量同步，由中心按批次幂等接收，避免重试或重复发送造成重复处理；同时结合多实例数据隔离和 Docker 化交付，明确数据与部署边界。
- **R**：分公司的 GitLab Commit 能在现有网络限制下接入中心质量看板。这段经历让我认识到，企业 Agent 的数据链路除了模型和工作流，还要处理网络边界、可靠传递和部署隔离；简历没有这一链路的吞吐、时延或可用性指标，我不会额外编造。

**追问：为什么不让中心直接拉取？**
中心不能主动访问分公司内网是既有约束。由 Edge 在分公司网络侧主动发起同步，更符合网络边界；具体网络和鉴权配置以企业安全规范为准，不把未写入简历的细节当成既有事实。

## 14. 讲一次你如何给 AI 编码工具设定边界？

- **S**：企业希望借助 Claude Code 或 Codex 快速完成 Agent MVP，但直接让工具在仓库中自由修改代码，容易出现上下文漂移、违反接口契约或绕过人工审批的问题。
- **T**：我需要让 AI 编程工具理解项目约束，同时保留关键业务责任的人审边界。
- **A**：我自建最小 AI Coding Harness，把架构约束、接口契约、测试策略、稳定决策和任务状态沉淀为 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等工程上下文，并设计“业务建模 → 任务单人工确认 → AI 编码与测试 → 人审验收 → 归档续接”的闭环。
- **R**：AI 的工作范围、验收方式和人工责任被明确固定下来，归档材料又能成为下一轮工作的上下文。它没有替代工程师，而是让 AI 编码更可控、可追溯。

## 15. 讲一次你如何划分模型与确定性系统的责任？

- **S**：质量管理中既有 BUG 严重等级、功能分布等结构化事实，也有质量体系 checklist、缺陷历史描述等不同类型的信息。
- **T**：我需要避免模型把统计事实和规范要求都当作自由生成问题处理。
- **A**：我设计“结构化业务数据经指标引擎计算、质量体系 checklist 经 RAG 提供依据”的边界，并使用 LLM 对缺陷历史记录进行需求变更标注后落库复用。模型只在工具结果和检索证据的范围内归纳，而不替代确定性计算。
- **R**：质量分析的责任边界更清楚：指标可追溯到计算结果，规范可追溯到文档依据，模型的作用是受约束地组织结论。数据不完整或证据不足时，系统应说明限制。

## 16. 讲一次你如何完成一条复杂 RAG 链路？

- **S**：论文引用查证需要从 PDF 中找到足以支持或否定引用合理性的上下文，单次模型阅读难以稳定给出可核验结果。
- **T**：我需要构建从论文解析到证据检索、引用判断和结构化输出的完整链路，并能评估检索和查证质量。
- **A**：我使用 GROBID 解析 PDF 并提取 TEI XML，完成文本切分、向量化、FAISS 检索和元数据过滤；再用 BM25、FAISS 与 Rerank 构建 Hybrid RAG。论文解析、上下文检索和引用验证被封装为工具，FastAPI 提供服务接口，并结合 Redis、Docker、日志和异常处理交付。评估上使用人工标注集，关注 Recall@k、证据覆盖率和判定准确率。
- **R**：系统能输出结构化的引用查证结果；当证据不足时返回“无法确认”。这保证了结果可被继续核验，而不是用语言流畅度代替证据。

## 17. 讲一次你如何处理实时数据与用户操作冲突？

- **S**：轻舟货运飞船前端需要周期性刷新遥测、报警、货物状态和语音事件，同时用户可能正在进行设备控制等操作。
- **T**：我需要保证实时事件触发后的页面一致性，又不能让后端状态回填覆盖用户正在进行的操作。
- **A**：我实现周期刷新、事件去重、全局路由跳转与状态管理；对用户交互期间的页面设计暂停和恢复状态刷新机制，并用 ECharts 展示遥测趋势，同时通过运行时配置适配不同后端服务地址。
- **R**：告警和语音指令触发后页面保持一致，用户操作期间不会被刷新数据直接覆盖。简历没有该前端的性能指标，因此我会说明设计目标和可观察行为，而不虚构响应时间。

## 使用与验收

1. 先脱稿讲第 1、3、5、13、16、17 题；它们覆盖动机、核心优势、代码评审、跨网同步、RAG 和全栈交互。
2. 每道 STAR 题控制在 60—90 秒：S/T 不超过 20 秒，A 说明技术动作和取舍，R 只讲简历支持的交付或风险控制。
3. 任何无法确认的个人职责都使用“我参与”“我负责其中的”或“按当前简历可确认的是”，不要把团队结果全部说成独立完成。
4. 录音复盘时只检查三件事：开头是否先给结论、是否说清个人动作、是否避免把设计机制夸大为量化结果。

## 1. 为什么转向 AI 应用 / Agent 方向？

### 参考回答

我本科和早期工作主要是物联网、前端和全栈开发，2023 年也参与过基于 OpenAI API 的内容生成与多平台发布流程。在接触 LLM 应用后，我发现模型能力只有和数据、工具、工作流、权限及业务流程结合，才能形成真正可用的产品。

因此研究生阶段我选择了人工智能方向，并持续投入 RAG、LangGraph、工具调用和 Agent 工程化实践。目前我在企业质量管理和代码评审场景中开发 Agent，也完成过论文引用查证 RAG 系统。我确认自己更适合做模型能力落地、可靠性设计和工程交付交叉处的工作。

### 可能追问与答案

#### AI 应用与传统全栈研发最大的差异是什么？

传统全栈研发中的很多逻辑是确定性的，输入、处理过程和输出相对可预期；AI 应用引入 LLM 后，输出具有概率性，因此不能只验证接口是否返回成功，还要关注回答是否有依据、是否符合结构、失败时是否安全。我的做法是将确定性逻辑交给工具、指标引擎或数据库，将文档依据交给 RAG，再让 LLM 在明确边界内归纳，并通过结构化输出、证据校验、人工确认和降级机制控制风险。

#### 为什么不选择大模型训练或纯算法方向？

我对模型原理和算法研究有兴趣，也有红外动作识别课题经历，但目前积累最完整、最能直接创造价值的能力是 AI 应用工程。我更擅长把模型接入真实数据和业务流程，处理工具调用、检索、接口、状态机、权限和异常恢复等问题。大模型训练和分布式训练是我需要继续补齐的方向，但现阶段我希望先在 Agent 和 AI 应用落地上形成更深的工程能力。

### 回答要点

- 过去的全栈经验是基础，不是与 AI 方向割裂的经历。
- 选择 Agent 是因为喜欢解决真实业务流程问题。
- 当前优势是模型能力落地，而不是声称自己擅长基础模型训练。

## 3. 你最大的技术优势是什么？

### 参考回答

我的优势是能从工程可靠性的角度落地 Agent。我不只关注模型回答是否流畅，还会先区分哪些信息必须由确定性系统提供、哪些需要检索依据、哪些可以交给 LLM 归纳。

例如在质量管理 Agent 中，我把结构化指标计算与质量体系 RAG 分开；在代码评审 Agent 中，要求结论关联文件、行号和快照 SHA，并对证据做校验。除此之外，我有后端、数据库和前端经验，所以也会考虑任务状态、权限、异常恢复和用户交互闭环。

### 可能追问与答案

#### 这是你的优势，有没有具体结果？

比较直接的结果是，代码评审 Agent 的每项结论都要求关联文件路径、行号和快照 SHA，模型引用不存在或证据不足时会降级为“无法确认”，而不是强行生成结论；质量管理 Agent 则将结构化指标计算和质量体系 RAG 分开，减少了把统计事实交给模型自由推断的风险。当前简历中没有统一的线上准确率指标，所以我会重点说明这些可验证的设计结果，并继续通过评估集、证据覆盖率和人工确认结果补充量化评估。

#### 与只会 Prompt 或只会后端的候选人相比，有什么不同？

我的特点是能把模型能力和工程系统结合起来。相比只关注 Prompt 的方式，我会考虑数据边界、工具权限、状态机、失败降级和审计；相比只关注后端的方式，我也会考虑模型输出不稳定、检索质量、证据引用和人工确认。比如我不仅参与了 Agent 的提示词和节点设计，也参与了 FastAPI、任务状态、缓存、权限和异常处理等工程环节。

### 关键词

`证据驱动`、`边界设计`、`受控工具`、`安全降级`、`工程闭环`。

## 5. 最有挑战的项目是什么？你承担什么职责？

### 推荐项目

优先回答“功能开发成果评审 Agent”；如果岗位偏 AI Coding 或研发效能，也可以回答“最小 AI Coding Harness”。

### 参考回答：成果评审 Agent

- **S**：项目需要从 GitLab 仓库中按 checklist 生成代码合规性评审草稿，但模型直接阅读代码容易编造依据，无法满足企业内部评审的可追溯要求。
- **T**：我需要参与设计一个既能自动化执行、又能保留人工确认和审计边界的评审流程。
- **A**：我参与拆分并实现 LangGraph 工作流中的仓库快照、事实提取、证据组装和逐项裁决等环节；为结论关联路径、行号和 SHA，并设计证据索引校验。对于任务执行侧，我参与梳理幂等创建、取消、重试与服务重启中断等状态迁移，避免长任务出现状态不一致。
- **R**：系统可以生成带证据的评审草稿，无法提供可靠证据时会降级为“无法确认”，由人工确认归档。这个过程使我积累了 Agent 可控性和长任务工程化的实践经验。

### 可能追问与答案

#### 你具体实现了哪些节点？

我重点参与了仓库快照、目录与依赖关系解析、事实提取、证据组装和逐项裁决等环节，同时参与了清单加载以及任务状态流转的设计。我的职责不是只写一个 Prompt，而是把每个节点的输入、输出、状态更新和异常分支定义清楚，让后续节点能够基于结构化结果继续执行。具体到团队协作边界，我会按照实际负责的模块说明，不把团队完成的部分全部归为个人成果。

#### 如何验证证据引用的合法性？

首先校验文件路径是否存在于指定仓库快照中；其次校验行号是否在文件有效范围内；然后确认引用使用的是本次任务对应的快照 SHA，而不是默认分支的其他版本。对于引用格式非法、文件不存在、行号越界或证据不足以支撑结论的情况，系统不采纳该结论，统一降级为“无法确认”，并保留失败原因供人工查看。

#### 如果评审任务运行中服务重启，如何恢复？

任务状态不能只保存在进程内存中，而要持久化任务状态、当前节点、进度、输入版本和错误信息。服务重新启动后，先识别处于执行中的任务，将其标记为“服务重启中断”或进入可恢复状态，再根据节点是否幂等决定从当前节点重试还是重新执行。对于已经产生外部副作用的步骤，需要通过幂等键或执行记录避免重复处理；无法安全恢复时，应进入失败或人工确认，而不是静默丢失任务。

## 6. 遇到需求变化时，你如何处理？

### 参考回答

- **S**：企业质量管理的分析诉求会随项目阶段变化，例如新增指标、新数据源或对结论依据提出更细要求。
- **T**：需要在不破坏既有流程的情况下快速支持变化，并保证历史任务可追溯。
- **A**：我会先澄清变化影响的是数据口径、业务规则、工具能力还是展示方式；然后将新增能力封装为独立工具或配置项，明确输入、输出和权限边界。涉及结论口径时，会保留版本和数据来源，避免同一问题在不同时间得到无法解释的结果。
- **R**：这种拆分使系统扩展尽量局限在对应工具、指标或 checklist 层，而不是修改整个 Agent 主流程。

### 可能追问与答案

#### 如果需求变化影响了已有数据库结构怎么办？

我会先确认这是字段新增、数据口径变化还是历史数据需要重算，再设计兼容迁移方案。数据库变更通过 Alembic 管理，优先采用向后兼容的新增字段或新表，先完成代码兼容和数据迁移，再切换读写逻辑；涉及历史口径时保留版本和来源，必要时进行回填与校验。对于不能一次完成的变更，会采用分阶段发布，避免新旧服务同时运行时出现数据不一致。

#### 如果产品要求先上线再补评估，你会怎么处理？

我会区分“上线功能”与“上线后不可观测”。如果评估集还没有完善，可以先以低风险范围、人工确认和明确降级机制上线，同时记录输入、工具调用、检索结果、模型输出和人工修改结果，建立最小可观测闭环。对于高风险结论，如果没有基本的证据校验和拒答机制，我不会建议完全自动化上线，而是先保留人工审核，之后用真实样本补充离线评估和线上指标。

## 7. 你如何处理技术分歧？

### 参考回答

- **S**：在 Agent 项目中，常见分歧是“是否让模型直接判断”与“是否增加确定性校验或人工确认”之间的效率和可靠性权衡。
- **T**：需要在交付速度、用户体验和业务风险之间达成可执行方案。
- **A**：我会先把争论转化为可验证的问题：结论的风险等级是什么、是否需要追溯依据、错误的代价是什么、能否通过小样本或评估集比较方案。对于高风险结论，我倾向于保留证据校验和人工确认；对于低风险摘要类能力，可以适度放宽自动化边界。
- **R**：团队讨论会从“谁的直觉更对”转为“在什么约束下选择什么方案”，最终方案也更容易被复用和解释。

## 8. 项目延期或任务推进受阻时，你如何处理？

### 参考回答

- **S**：Agent 项目通常涉及外部数据源、代码仓库权限、文档质量和模型输出稳定性，任何一项都可能拖慢整体进度。
- **T**：在保证核心价值的前提下控制风险，并让协作方及时知道阻塞点。
- **A**：我会把任务拆成可独立验证的最小链路，优先保障“数据获取 → 工具/检索 → 有证据的结果输出”主流程；对于不稳定能力设置 mock、降级或人工确认。出现阻塞时明确记录依赖方、影响范围、替代方案和需要决策的事项，而不是等到截止时间才反馈。
- **R**：即使部分增强能力延后，也能先交付可验证的 MVP，并为后续迭代保留清晰边界。

## 9. 讲一次你如何处理异常或失败结果？

### 参考回答

- **S**：在论文引用查证场景中，PDF 解析可能失败，或检索结果无法覆盖引用判定所需的上下文。
- **T**：不能因为系统无法确认就生成貌似合理的判断。
- **A**：我将解析、检索和判定拆开处理：解析失败时返回明确失败原因；检索证据不足时将结果标记为“无法确认”，并保留已检索到的证据和限制说明；接口侧结合日志和异常处理，便于定位具体失败阶段。
- **R**：系统虽然会在部分样本上拒答，但避免了无证据结论，符合引用查证场景对可靠性的要求。

## 12. 你从一段失败或不足的经历中学到了什么？

### 参考回答

我在做 LLM 应用时逐渐认识到，Demo 很容易只关注“能否生成看起来正确的答案”，而忽略答案的来源、错误成本和不可复现问题。后来在质量分析和代码评审场景中，我把这种认识转化为具体设计：将结构化计算、检索依据和 LLM 归纳分层；对高风险结论增加证据校验与人工确认；对证据不足的结果明确降级。这个变化让我从“功能实现”进一步关注“系统是否值得被信任”。

## 十三、通用追问答题原则

- 先给结论，再说明背景和原因。
- 优先使用“我负责”“我设计”“我实现”，准确区分个人职责与团队成果。
- 每个答案至少包含一个具体场景、一个技术动作和一个结果或复盘。
- 没有量化指标时，说明验证方法、观察结果或当前限制。
- 不编造数据；不确定时说明“这部分我没有直接负责，但我的理解是……”。

## 四、5 分钟项目导向版

### 版本 A：质量管理体系 Agent

我想重点介绍一下我在实习中参与的质量管理体系 Agent。它面向企业内部质量管理场景，接入禅道 BUG 数据、GitLab Commit、飞书需求文档和质量体系文件，目标是帮助研发和质量团队查询质量指标、分析缺陷问题，并给出有依据的质量分析结果。

这个项目一开始最重要的判断是，不能把所有材料直接交给大模型后让它自由回答。BUG 严重等级、模块分布、激活情况等属于结构化业务事实，如果依赖模型从大量文本中归纳，容易产生统计错误；质量体系 checklist、流程规范等属于文档知识，需要给出原始依据。因此我们把系统拆成三部分：结构化数据经过指标引擎和受控工具计算；质量体系文件通过 RAG 检索并返回相关依据；LLM 负责识别用户意图、编排工具调用，并在事实和依据的范围内生成结果。

在工作流上，我们使用 LangGraph 组织“意图识别 → 受控工具调用 → 结果生成”的流程。我的工作重点之一是工具注册与调用边界：将缺陷等级、功能分布、激活、需求变更等指标封装为独立工具，使每个工具都有明确的输入参数、返回结构与调用范围。这样一方面方便后续扩展新的指标，另一方面也避免模型直接拼接不受控的查询或跨权限访问数据。

数据接入也存在网络边界：中心系统无法主动访问分公司内网的 GitLab。我在该模块实现 Edge 端主动同步，以 SQLite Outbox 保存待同步数据、通过游标定位增量、由中心按批次幂等接收，并配合多实例数据隔离和 Docker 化交付。这里的取舍是让数据从受限网络一侧主动发起同步，而不是要求中心直接跨网拉取；我不会把这项实现表述为未经验证的实时性、吞吐或“零丢失”指标。

另一个难点是需求变更的判定。缺陷历史记录中存在大量非结构化描述，单纯依赖规则覆盖有限。我们使用 LLM 对历史记录进行需求变更标注，并将结果落库复用；但这个标注不直接等同于最终事实，而是作为后续分析可复查的数据。对于真正需要确认的业务结论，仍要回到原始记录、指标结果和质量体系依据。

这个项目的核心价值在于建立责任边界：结构化指标由确定性计算负责，规范解释由 RAG 提供证据，LLM 负责受约束的归纳。当数据不完整或检索不到依据时，系统应明确说明限制，而不是生成看似合理但没有支撑的结论。

如果继续迭代，我会优先完善三点：第一，构建典型质量问题的离线评估集，评估工具选择和回答依据的准确性；第二，为关键结论增加更细粒度的数据来源和时间范围展示；第三，补充工具调用、检索命中与回答结果的链路追踪，便于线上排障和持续优化。

### 版本 B：功能开发成果评审 Agent

这个项目面向 GitLab 代码仓库，目标是根据既定 checklist 自动生成可追溯的合规性评审草稿，并由人工确认归档。项目的关键不是让模型“看起来像在审代码”，而是确保每项结论都有具体证据。

因此我们设计了从清单加载、仓库快照、目录与依赖关系解析、事实提取、证据组装到逐项裁决的 9 节点 LangGraph 工作流。评审结论不只是一句自然语言，而要关联文件路径、行号和仓库快照 SHA。对于 LLM 返回的证据引用，系统会做索引校验；引用不存在、越过快照边界或不足以支撑结论时，统一降级为“无法确认”。

工程上，我们还设计了覆盖创建、执行、待人工确认、取消、失败和服务重启中断处理的任务状态机，并支持幂等创建、进度跟踪、取消/重试和审计记录。源码使用只读 GitLab Token 获取且不落库，同时限制文件大小与并发，控制安全和资源风险。

这个项目让我最深的体会是，企业 Agent 的难点往往不是“让模型能调用工具”，而是如何管理任务生命周期、约束模型证据、保留人工责任边界，并在失败时以安全方式降级。

### 版本 C：最小 AI Coding Harness

这个项目的背景是，企业希望使用 Claude Code 或 Codex 这样的 AI 编程工具快速完成 MVP 开发，但直接让 Agent 在仓库中自由修改代码会带来几个问题：它不了解项目的稳定架构决策和接口约束，任务边界容易漂移，生成代码也可能绕过测试和人工审批。

因此我自建了一个最小 AI Coding Harness，目标不是替代工程师，而是为 AI 编程工具提供受控的协作框架。我把架构约束、接口契约、测试策略、已确认的稳定决策和任务状态沉淀为结构化工程上下文，形成 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等协作材料。这样 Agent 在开始编码前可以先理解任务范围、不能违反的契约和验收方式，而不是只根据一句自然语言需求猜测实现。

在流程上，我设计了“业务建模 → 任务单人工确认 → AI 编码与测试 → 人审验收 → 归档续接”的闭环。人工确认不是为了降低自动化程度，而是把业务目标、改动范围和关键责任在编码前锁定；AI 负责在明确任务单下生成和验证代码；人审决定是否接受变更；归档后的任务、决策和契约又成为下一轮工作的可靠上下文。

这个项目让我关注到 Coding Agent 的核心挑战是上下文工程和治理，而不是单次代码生成效果。后续如果继续迭代，我会增加任务与代码变更的可追溯关联、自动化测试结果采集、权限分级以及针对不同仓库的上下文初始化机制，并通过任务完成率、返工率、测试通过率和人工修改率评估它的效果。

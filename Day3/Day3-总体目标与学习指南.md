## 一、当天在十天计划中的位置

Day 1 完成岗位定位和开场介绍，Day 2 展示了质量管理体系 Agent 如何把结构化事实、RAG 依据和 LLM 归纳分开；Day 3 进一步说明我如何把这种“受控、可追溯、有人负责”的思路放到 AI Coding 场景。

本日围绕简历中的两项工作展开：

1. **功能开发成果评审 Agent**：对指定 GitLab 仓库快照进行只读 checklist 评审，生成带证据链的草稿，人工确认后归档。
2. **最小 AI Coding Harness**：为 Claude Code / Codex 等工具提供任务单、架构决策、接口契约和测试计划，使 AI 编码有明确边界、可续接上下文和人工审批点。

两者不是同一个系统：Harness 约束“如何开发”，评审 Agent 约束“如何审查开发成果”；它们共同体现的不是“让模型自动完成一切”，而是让模型在明确事实、测试和人工责任边界内提高效率。

## 二、简历对应与个人职责

### 功能开发成果评审 Agent

- 面向 GitLab 代码仓库设计和实现证据驱动的 checklist 合规性评审 Agent。
- 参与设计评审流程、证据数据结构、LLM 引用校验、任务状态机、安全与资源控制。
- 输出的是**可追溯的评审草稿**，由人工确认后归档；不向 GitLab 写评论、MR 或 Issue。

### 最小 AI Coding Harness

- 为企业 Agent MVP 沉淀 `dev_tasks`、`decision_log`、`api_contract`、`test_plan` 等工程上下文。
- 参与建立“业务建模 → 任务单人工确认 → AI 编码与测试 → 人审验收 → 归档续接”的受控开发闭环。
- 不把这段经历表述为训练模型、替代工程师或全自动研发。

## 四、必须统一的事实口径

### 1. “9 节点”与当前代码的区别

简历和架构材料把清单加载、快照、目录解析、依赖解析、事实提取、证据组装、逐项裁决、结论持久化、报告装配概括为 **9 个业务阶段**。

但当前 `agent_research/app/agents/code_review_graph.py` 的 `build_code_review_graph()` 实际注册了 **7 个 LangGraph 节点**：`load_checklists`、`collect_snapshot`、`build_inventory`、`extract_relations`、`extract_repository_facts`、`build_evidence_packs`、`adjudicate`。结论持久化和报告装配在 `CodeReviewTaskService._run_background()` 中完成，不是图节点。

**面试安全说法**：

> 我把整体执行链路概括为 9 个业务阶段；其中当前 LangGraph 图承载前 7 个受控分析节点，服务层负责结论持久化和报告草稿装配。这样把编排和任务生命周期分开，状态恢复、审计和资源控制更清晰。

不要脱离代码直接说“当前实现有 9 个 LangGraph 节点”。如简历后续继续保留“9 节点”表述，应在面试前确认是否需要同步为“9 个业务阶段”。

### 2. 事实与方案的边界

- 已实现/代码可见：只读 GitLab 快照、固定 SHA、受控工具、证据定位、结构化裁决校验、任务状态、取消/重试/中断标记、审计、源码不落库、文件与并发限制。
- 可作为后续优化：更丰富的静态分析、基于人工反馈的规则改进、更多语言/框架的关系解析、评审一致性评测。
- 未确认的信息：线上使用规模、命中率、耗时收益、模型名称、生产部署数量、个人独立完成比例。未核对前不做确定性表述。

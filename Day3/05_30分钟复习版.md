# Day 3：30 分钟复习版——成果评审 Agent 与 AI Coding Harness

> **目标**：只记两条线：开发时如何约束 AI，评审时如何约束 AI；共同落点是“上下文、证据、测试、人工责任”。

## 0–5 分钟：两个 30 秒答案

### 成果评审 Agent

> 它面向 GitLab 仓库做只读 checklist 评审。系统固定仓库快照 SHA，提取目录、依赖和仓库事实，按条目组装候选证据；LLM 只在这些证据范围内生成裁决草稿。每个结论关联路径、行号、SHA 和 checklist 来源，非法引用或证据不足时降级为“证据不足或无法确认”，最终由人工确认归档。

### AI Coding Harness

> Harness 是给 Claude Code / Codex 等工具准备的受控研发上下文：任务单定义范围和验收，决策记录保存已确认取舍，接口契约固定兼容边界，测试计划明确验证方式。AI 在这些约束内编码和测试，人负责任务确认、代码验收和归档。

## 5–12 分钟：一张双主线图

```text
开发约束（Harness）
业务建模 → dev_tasks → decision_log / api_contract / test_plan
        → AI 编码与测试 → 人审验收 → 归档续接

评审约束（Review Agent）
checklist → 固定 snapshot SHA → 目录/关系/事实 → 证据包
        → LLM 裁决 + 引用校验 → 草稿 → 人工确认归档
```

### 必须主动说清的事实

- 当前实现可讲为 **9 个业务阶段**，其中 `build_code_review_graph()` 实际有 **7 个 LangGraph 图节点**；持久化 findings 和报告装配在服务层。
- Harness 管“怎么开发”，评审 Agent 管“怎么形成可信评审结论”；不是同一个系统。

## 12–20 分钟：8 个必答问题

### 1. 为什么不让 LLM 直接读完整仓库后下结论？

> 全量代码会带来上下文截断、成本、噪声和敏感信息暴露，也不能保证模型引用真实位置。应该先固定版本和范围，再提取与条目相关的事实和候选证据。

### 2. 为什么结论必须绑定 SHA？

> 分支会变化，路径和行号会漂移；固定 SHA 把结论、证据和被评审对象锁在同一不可变版本上，才能复现和审计。

### 3. 如何防止模型编造路径和行号？

> 系统先生成候选证据和索引，模型引用索引；服务端校验索引是否存在、是否属于当前条目、结构是否合规。非法引用不能形成确定结论。

### 4. “不符合”和“无法确认”区别？

> 不符合有足够反证或确定性规则支持；无法确认是当前范围和证据不足。前者是发现风险，后者是要求补证或人工核查。

### 5. 创建幂等、取消和重试怎么做？

> 创建用 `idempotency_key` 避免重复任务；取消先写 `cancel_requested`，由安全检查点协作式停止；`failed`、`canceled`、`interrupted` 重试时创建新任务并关联原任务。

### 6. 服务重启如何处理任务？

> 启动时把遗留活动任务标记为 `interrupted` 并写审计，不在读取接口自动续跑；人工决定是否重试，避免不确定上下文下重复执行。

### 7. 为什么源码不落库？

> 源码敏感且落库扩大权限和泄露面。分析可在内存中完成，持久化只留 SHA、路径、行号、哈希、事实、结论和报告元数据；复查回到有权限的 GitLab 提交。

### 8. 什么是足够的 Context Engineering？

> 不是完整仓库，而是任务边界和版本、相关架构、已确认决策、接口契约、测试计划和关键调用链。信息不足继续检索或交给人，不让模型补全猜测。

## 20–27 分钟：三句高频总结

1. **证据原则**：“模型负责归纳，不是证据来源；证据来自固定仓库快照。”
2. **开发原则**：“AI 可以生成候选实现，但任务范围、业务规则、测试与最终交付责任仍在人。”
3. **安全原则**：“评审采用只读权限、源码不落库、资源限制和人工确认，避免让自动化扩大风险。”

### 白板速画：状态机

```text
queued → validating → collecting → evaluating → assembling → pending_review → human_confirmed
活动状态 → cancel_requested → canceled
活动状态 → failed
服务重启时活动状态 → interrupted
failed / canceled / interrupted → 新任务 queued（retry_of_task_id）
```

# Day 3：项目与技术问答

> 使用方式：先遮住答案口述，再对照补齐事实边界。答案基于当前简历与 `agent_research` 代码；未确认的线上指标、模型和部署信息不补充。

---

## 1. 请介绍功能开发成果评审 Agent。

**答案**：它面向 GitLab 仓库做只读 checklist 评审：先固定仓库快照 SHA，再解析目录、依赖和仓库事实，为每个条目组装候选证据；LLM 只在证据范围内生成裁决草稿。结论关联路径、行号、SHA 和 checklist 来源，并校验引用合法性；无证据或引用异常时降级为“证据不足或无法确认”，人工确认后才归档。

**追问**：你个人负责什么？  **答**：按简历口径，我参与工作流、证据驱动裁决、状态机及安全/资源控制相关能力；具体独立完成比例以实际协作记录为准。

## 2. LLM 能读代码，为什么还要快照、事实提取和证据组装？

**答案**：模型能读局部不等于能给可审计结论。快照固定版本，目录/关系解析补足范围和调用上下文，事实提取压缩可复用信息，证据组装把每个条目的候选范围收敛，降低全仓输入成本、噪声和幻觉风险。

**追问**：会不会漏检？  **答**：会有覆盖边界，必须记录跳过文件和限制；未覆盖不能说通过，可用解析器、扫描器和人工抽查补强。

## 3. 为什么要绑定 `snapshot_sha`，而不是分支名？

**答案**：分支是可变引用，提交后代码和行号都会漂移。SHA 指向不可变提交，使结论、证据和评审对象一致，可复现、可审计。

**追问**：用户指定分支怎么办？  **答**：分支可作为输入，但采集时解析为具体 SHA；报告同时记录请求分支与最终快照，结论只对该快照负责。

## 4. 如何避免模型编造路径或行号？

**答案**：先从固定快照产生受控候选证据与索引，模型引用索引而不是自由生成路径；服务端校验索引存在、归属当前条目、状态与证据数量匹配，并校验结构化输出。无效时保守降级。

**追问**：只靠 prompt 行不行？  **答**：不行。提示词只能降概率，证据存在性和范围关系必须由确定性代码验证。

## 5. “不符合”和“证据不足或无法确认”有什么区别？

**答案**：不符合需要充分反证或确定性规则证明未满足；证据不足表示当前范围无法可靠判断，如文件被跳过或上下文不完整。前者是风险发现，后者是待补证/扩大范围项。

**追问**：“符合”是否代表绝对没问题？  **答**：不是，只代表固定快照、当前条目和当前范围内符合，仍要保留限制说明。

## 6. 为什么说 9 个阶段，但代码中只有 7 个 LangGraph 节点？

**答案**：9 个是完整业务阶段：前 7 个分析步骤由 LangGraph 承载，findings 持久化与 Markdown 草稿装配在任务服务层完成。编排与生命周期分开后，事务、报告、状态和恢复更清晰。

**追问**：简历“9 节点 LangGraph”如何答？  **答**：以代码为准说“9 个业务阶段，其中当前 LangGraph 有 7 个图节点”；面试前应同步确认简历措辞。

## 7. 如何支持新的 checklist，而不重写流程？

**答案**：工作流只处理通用步骤：加载条目、采集事实、组装证据、逐项裁决。新 checklist 只要按条目结构提供来源、版本和规则即可进入同一链路；若需要新证据能力，再增加受控工具/解析器并补测试。

**追问**：规则本身如何追溯？  **答**：条目保存来源路径、来源 SHA 和行号，报告记录所用版本。

## 8. 任务状态机有哪些核心状态？

**答案**：主线是 `queued`、`validating`、`collecting`、`evaluating`、`assembling`、`pending_review`、`human_confirmed`；异常控制有 `cancel_requested`、`canceled`、`failed`、`interrupted`。重点是业务含义和迁移，而不是死背数量。

**追问**：为什么不能运行中直接人工确认？  **答**：确认前必须有完整草稿、证据和报告，因此先进入 `pending_review`。

## 9. 创建幂等如何设计？

**答案**：创建接口支持 `idempotency_key`，数据模型为其做唯一约束。重复请求先返回已有任务而不再次启动后台执行，防止网络重试、双击和请求重放产生重复评审。

**追问**：重试是否复用原任务？  **答**：不会直接改回运行中；`failed`、`canceled`、`interrupted` 会创建新任务，并用 `retry_of_task_id` 关联旧任务保留审计。

## 10. 取消与任务完成同时发生，如何避免状态错乱？

**答案**：取消接口先写 `cancel_requested`，执行器在安全检查点读取该状态；图执行返回、落草稿前也再检查。以数据库状态和协作式检查点协调，不依赖前端按钮时序。

**追问**：为什么不强杀线程？  **答**：强杀会让事务、网络连接和文件写入不可预测；协作式取消能在明确边界停下并记录审计。

## 11. 服务重启时正在执行的任务如何处理？

**答案**：服务启动时扫描上次进程遗留的活动任务，统一标为 `interrupted`，写稳定错误码和审计；读取接口不触发恢复，之后由人工决定是否重试。

**追问**：为什么不自动续跑？  **答**：自动续跑需要可靠断点、外部快照一致性和幂等保障；当前保守策略避免在不确定上下文里重复调用。

## 12. 如何处理大仓库和慢请求？

**答案**：限制并发任务、单文件大小、文件数量、总字节数和 blob 读取并发；GitLab/LLM 调用及关键阶段有 timeout/deadline；进度服务记录心跳与处理计数。超限或跳过必须进入限制说明。

**追问**：为什么不无限并发？  **答**：会压垮 GitLab、LLM 配额、数据库连接或内存；上限是吞吐、延迟和外部稳定性的取舍。

## 13. 为什么源码不落库？审计如何保留？

**答案**：源码敏感，落库扩大权限、备份和泄露面。源码在内存中分析，持久化时去掉文件正文；审计保留 SHA、文件定位、内容哈希、统计、证据关系、结论和报告哈希，复查时回到有权限的 GitLab 固定提交。

**追问**：摘录也敏感怎么办？  **答**：按数据分级限制摘录、脱敏和访问权限；极敏感场景只保存定位与哈希。

## 14. 为什么必须使用只读 GitLab Token？

**答案**：评审只需要读取和分析，不需要写仓库。最小权限能限制 prompt 注入、实现缺陷或误操作的影响，模型即使输出异常也无法评论、改分支、建 MR 或合并。

**追问**：以后自动提 Issue？  **答**：应做成独立、显式授权的写操作流程，增加人审、细粒度权限、幂等和审计，不能悄悄扩展当前链路权限。

## 15. 什么是 Evidence-Grounded，而不是普通 LLM 审查？

**答案**：它以固定快照中的可定位证据为结论基础，模型只在条目规则和候选证据间归纳。结果同时包含理由、路径、行号、版本和规则来源，并由程序校验证据引用。

**追问**：能完全消除幻觉吗？  **答**：不能；它降低无依据结论并提高可发现性，解析遗漏、语义偏差和规则不完备仍需测试和人审。

## 16. 如何评估评审 Agent 的可靠性？

**答案**：建立人工标注的 checklist 样本，以固定快照为单位看条目覆盖率、合法证据引用率、无证据降级正确性、与人工评审一致性、错误类型和人工修改率；同时观察耗时、超时、取消、失败和跳过比例。简历未给具体指标时只讲方法。

**追问**：误判后怎么改？  **答**：保留脱敏任务元数据、SHA、条目版本、证据和人工修订原因，定位解析、证据组装、裁决还是规则的问题，修复后纳入回归集。

## 17. AI Coding Harness 是什么？

**答案**：它是面向 AI 编程工具的工程上下文和执行协议。通过任务单、决策记录、接口契约和测试计划，把目标、边界、已确认取舍和验收从聊天记忆变成可复用的仓库资产，并保留人工确认点。

**追问**：和提示词模板有什么区别？  **答**：模板主要影响一次对话；Harness 把约束放到版本化文档、目录、任务状态和测试规范中，可跨会话和工具续接。

## 18. Repo 级任务中，什么是足够的 Context Engineering？

**答案**：不是全量代码，而是让模型能判断改动边界和验证方式：任务单、当前版本、相关架构和决策、接口契约、测试计划以及关键调用链。信息不够继续检索；字段、枚举、阈值未确认时记录待确认项并交给人。

**追问**：为什么不把完整仓库塞进上下文？  **答**：成本、噪声和敏感数据暴露会扩大，无关代码和旧文档会稀释关键约束。

## 19. Harness 与成果评审 Agent 如何形成闭环？

**答案**：Harness 约束“为什么改、改哪里、接口和测试如何验证”；评审 Agent 约束“按哪版 checklist、基于哪个快照、用哪些证据形成草稿”。前者让开发过程可控，后者让评审结果可追溯，通过任务、测试和人工验收连接但不互相替代。

**追问**：能让评审结果自动改代码吗？  **答**：当前不应自动写回；评审结果可转为新的任务单，经人工确认范围和优先级后再由 Harness 约束修改。

## 20. 为什么 AI 生成代码后仍要保留人工确认、测试计划和代码审查？

**答案**：候选代码不等于业务正确、兼容、安全和责任已经被接受。人工确认负责问题定义和范围，测试计划负责可重复验证，评审与人审共同承担交付责任；AI 的作用是加速这些环节，而不是取消它们。

**追问**：这会不会降低效率？  **答**：短期多了建模和审查步骤，但降低返工、上下文丢失和不可追溯变更；企业工程更重视稳定交付与风险可控。
